Chunking Strategies

How to preserve meaning, enforce model limits, control cost, and retrieve the smallest evidence that still contains enough context to answer correctly.

Explore strategies →Production blueprint
Mental model

Chunking Is a Retrieval Design Decision

A chunk is simultaneously an embedding input, a retrieval unit, and evidence shown to the generator. Optimizing only its character count usually fails.

🎯 Precision

Smaller, topically focused chunks create less embedding dilution and fewer irrelevant tokens in the answer context.

🧭 Context

Larger chunks preserve definitions, headings, references, table labels, and the evidence needed to answer completely.

⚖️ The trade-off

The goal is not “the perfect size.” It is the smallest independently meaningful unit, bounded by the embedding model.

From Structured Document to Retrieval Units
Structure proposes safe boundaries; semantics refines them; token accounting enforces the hard contract.
→
Chunk A · heading + coherent paragraphs · 386 tokens
Chunk B · table caption + headers + rows · 441 tokens
Chunk C · inherited section path + code block · 318 tokens
Production default: parse structure first, preserve atomic elements, split or merge using semantics where valuable, then enforce a tokenizer-based hard maximum. Start simple and prove every added layer with retrieval evaluation.
Seven approaches

How Each Strategy Behaves

The most common production choices are recursive, structure-aware, Docling hybrid, and parent-child—often combined rather than used alone.

1

Recursive Character Chunking MOST USED BASELINE

Deterministic splitting with progressively weaker separators

How it works

Attempts separators in priority order—commonly double newline, newline, sentence-like space, then characters—until every piece fits. It is “recursive” because oversized pieces are retried with the next separator. Size may be characters or a supplied token-length function.

When to use

General text, Markdown, support articles, MVPs, and a robust fallback after parsers fail.

Typical size

300–800 embedding tokens; 10–20% overlap. If configured in characters, calibrate against actual tokenizer distributions.

Advantages

  • Fast, cheap, deterministic
  • Easy to debug and re-index
  • Strong baseline across domains

Disadvantages

  • Blind to document semantics
  • Can detach headings or table labels
  • Character counts do not guarantee token limits

Retrieval impact

Good when topics follow paragraphs. Precision drops when mixed topics enter one chunk; recall drops when answers cross boundaries.

Cost & production suitability

Cost: very low, linear scan. Suitability: excellent baseline; add metadata and token enforcement.

2

Structure-Aware Chunking COMMON IN PRODUCTION

Uses headings, paragraphs, lists, tables, pages, and code blocks as boundaries

How it works

A parser builds a document tree or typed blocks. The chunker groups sibling blocks under the same heading, preserves atomic blocks when possible, and carries the section path, captions, page numbers, and element types as metadata.

When to use

PDFs, manuals, policies, contracts, technical docs, Markdown/HTML, research papers, and code repositories.

Typical size

One logical section or block group, usually 300–1,000 tokens, with a hard token cap and no arbitrary overlap inside tables/code.

Advantages

  • Preserves human-authored organization
  • Excellent explainability and citations
  • Better handling of tables and code

Disadvantages

  • Depends on parser quality
  • Scanned/OCR PDFs produce noisy structure
  • Sections vary dramatically in size

Retrieval impact

Usually improves precision because heading context disambiguates content. Bad layout detection can silently damage both recall and ordering.

Cost & production suitability

Cost: low–medium; parsing/OCR dominates. Suitability: excellent when the corpus has reliable structure.

3

Semantic / Embedding-Based Chunking SELECTIVE USE

Places boundaries where adjacent sentence windows change meaning

How it works

Split into sentences, create overlapping sentence windows, embed each window, calculate adjacent cosine distance, and cut where the distance exceeds a percentile, standard-deviation, gradient, or absolute threshold. Some implementations then merge neighboring coherent units.

When to use

Long narrative text, transcripts, mixed-topic notes, and documents whose topical boundaries are not represented by headings.

Typical size

Variable, commonly targeted at 200–800 tokens. Always add a hard maximum (often 800–1,200) plus a minimum to prevent tiny fragments.

Advantages

  • Topically coherent chunks
  • Fewer arbitrary mid-thought cuts
  • Can improve precision on topic transitions

Disadvantages

  • Embedding pass increases cost/latency
  • Thresholds are model/domain sensitive
  • Similar prose can merge into huge chunks

Retrieval impact

Can improve relevance where topics drift, but is not automatically better. Oversized coherent chunks dilute vectors; tiny chunks lose evidence.

Cost & production suitability

Cost: medium–high at indexing. Suitability: conditional; pin models, cache sentence embeddings, enforce limits, evaluate.

Why can it create excessively large chunks? If adjacent windows remain semantically similar, no breakpoint fires—even if the accumulated text exceeds the embedding model’s limit. Semantic cohesion is a soft signal, not a size guarantee.
4

Docling HybridChunker PDF-FIRST CHOICE

Document hierarchy plus tokenizer-aware split/merge refinement

How it works

Docling first parses the file into a structured DoclingDocument. HybridChunker begins with hierarchical chunks, splits only chunks that exceed the configured tokenizer budget, and—by default—merges undersized adjacent peers that share headings/captions. Its contextualizer serializes relevant metadata with the chunk.

When to use

Layout-heavy PDF, DOCX, PPTX, reports, papers, manuals, and documents containing tables/captions.

Typical size

Set max_tokens to the embedding model’s effective limit minus enrichment/special-token reserve; often 400–800.

Advantages

  • Preserves parsed hierarchy and metadata
  • Tokenizer-aware hard sizing
  • Repeats table headers across split chunks
  • Merges compatible tiny peers

Disadvantages

  • Parsing/OCR can be expensive
  • Depends on layout recognition quality
  • Not a semantic topic-change detector by itself

Retrieval impact

Strong for PDFs because captions, section paths, and table headers remain attached. Contextualized text improves standalone chunk meaning.

Cost & production suitability

Cost: medium; mostly parsing. Suitability: high for enterprise documents, with parser QA and pinned versions.

5

Parent-Child / Hierarchical Chunking HIGH-VALUE PATTERN

Retrieve with small children; answer with larger parents

How it works

Index small child chunks for precise vector matching. Each child stores a parent_id. At query time, retrieve top children, map them to their larger parent sections, deduplicate parents, optionally rerank, and pass those parents to the generator.

When to use

Answers need a surrounding procedure, definition, legal clause, or several adjacent facts—not just the matching sentence.

Typical size

Children: 150–400 tokens. Parents: 800–2,000 tokens or a coherent section. Parent must still fit the generation budget.

Advantages

  • Combines retrieval precision with answer context
  • Reduces need for large child overlap
  • Natural citations at section level

Disadvantages

  • Two stores and ID integrity required
  • Multiple hits may inflate context
  • Large parents can add irrelevant content

Retrieval impact

Often raises answer completeness without sacrificing child-level recall. Deduplication and parent reranking are essential.

Cost & production suitability

Cost: medium storage/orchestration. Suitability: excellent for complex QA and long-form documents.

6

Hybrid Chunking Approaches RECOMMENDED END STATE

Combines deterministic structure, semantic signals, and hard token constraints

How it works

A policy chain chooses boundaries in order: preserve atomic structure → detect semantic transitions within oversized narrative sections → enforce token maximum recursively → merge tiny compatible neighbors → enrich with metadata. Different element types receive different policies.

When to use

Mixed enterprise corpora, high-value search, many file types, or when one strategy cannot safely handle prose, tables, and code.

Typical size

Target 300–700 tokens, hard max aligned to embeddings, minimum 80–150; overlap only for boundary-sensitive prose.

Advantages

  • Best balance of quality and control
  • Element-specific behavior
  • Graceful fallback path

Disadvantages

  • More policies and observability needed
  • Harder to reproduce/debug
  • Benefits may not justify complexity

Retrieval impact

Potentially highest quality because both logical and topical boundaries are respected. Gains must be measured by corpus/query segment.

Cost & production suitability

Cost: medium–high. Suitability: high after a simpler baseline establishes measurable gaps.

7

LLM-Based Chunking ADVANCED / OFFLINE

Uses a language model to identify discourse units or label boundaries

How it works

An LLM receives a bounded document window and returns sentence-boundary indices, section labels, or structured JSON describing self-contained units. A deterministic post-processor validates offsets, enforces token limits, and falls back when output is invalid.

When to use

High-value, low-volume domains where implicit discourse matters: complex policies, clinical literature, legal analysis, or curated knowledge bases.

Typical size

Prompt for 400–1,200-token units, but always validate with the embedding tokenizer and split oversized output deterministically.

Advantages

  • Understands discourse and implicit context
  • Can add titles/summaries while chunking
  • Domain instructions are expressive

Disadvantages

  • Highest cost and latency
  • Nondeterminism and malformed offsets
  • Privacy, rate-limit, and model-drift risks

Retrieval impact

Can excel on nuanced corpora, but summaries may distort evidence and model changes can alter every boundary. Preserve source spans.

Cost & production suitability

Cost: very high. Suitability: niche; batch-only, cached, versioned, validated, and evaluated against simpler methods.

A Layered Ingestion Pipeline

Treat chunking as a versioned transformation with explicit contracts, metrics, and reproducible outputs.

Stage responsibilities

  1. Parsing: recover reading order and typed elements; retain source coordinates.
  2. Structure detection: create heading ancestry, table/caption links, list/code boundaries.
  3. Semantic/hybrid chunking: form independently meaningful candidate units.
  4. Token enforcement: count exactly as the embedding model does; reserve enrichment tokens.
  5. Context enrichment: prepend concise document title/section path; keep raw text separately.
  6. Embedding/indexing: batch, normalize as required, upsert idempotently, and filter by active version.

Recommended policy

  • Start with structure-aware or recursive token-aware chunks.
  • Route tables, code, and narrative prose to separate chunk policies.
  • Use semantic splitting only inside oversized prose sections—not across document hierarchy.
  • Use child vectors + parent expansion when complete answers need more context.
  • Record parser_version, chunker_version, tokenizer/model IDs, parameters, and content hashes.
  • Canary re-index and compare Recall@K, Precision@K, answer faithfulness, latency, and cost.

Why HybridChunker is useful—and how to combine it

PDF text extraction alone loses hierarchy, captions, and table meaning. Docling keeps those relationships and then makes the hierarchy safe for a real tokenizer. Configure it with the embedding tokenizer and an effective budget such as model_limit - enrichment_reserve - special_tokens. For large narrative sections, optionally run semantic breakpoint detection within that section first, then pass every result through token enforcement. Do not semantically split table rows or code blocks blindly; use Docling’s structural/line-aware handling and repeat table headers when a table spans chunks.

Layer order matters: structure constrains where semantic splitting is allowed; token limits are the final authority. Semantic similarity must never override the embedding model’s hard input limit.
Small practical examples

Code Patterns

APIs evolve: pin exact package versions, test representative files, and treat examples as focused building blocks rather than a complete ingestion service.

1. Recursive chunking — langchain-text-splitters

recursive_chunking.py
from langchain_text_splitters import RecursiveCharacterTextSplitter
from transformers import AutoTokenizer

tok = AutoTokenizer.from_pretrained("BAAI/bge-small-en-v1.5")
splitter = RecursiveCharacterTextSplitter(
    chunk_size=480, chunk_overlap=60,
    length_function=lambda s: len(tok.encode(s, add_special_tokens=False)),
    separators=["\n\n", "\n", ". ", " ", ""],
)
chunks = splitter.create_documents([text], metadatas=[{"doc_id": doc_id}])
Package: langchain-text-splitters. Production: yes—mature and deterministic; use an embedding-tokenizer length function rather than relying on characters.

2. Token-based chunking — Hugging Face transformers

token_windows.py
from transformers import AutoTokenizer

tok = AutoTokenizer.from_pretrained("BAAI/bge-small-en-v1.5", use_fast=True)
ids = tok.encode(text, add_special_tokens=False)
size, overlap = 480, 60
chunks = [
    tok.decode(ids[i:i + size], skip_special_tokens=True)
    for i in range(0, len(ids), size - overlap)
]
assert all(len(tok.encode(c, add_special_tokens=False)) <= size for c in chunks)
Package: transformers (Hugging Face). Production: yes for exact counting; raw token windows may split sentences or decode imperfectly, so prefer them as a final enforcement/fallback layer.

3. Semantic chunking — LangChain status and alternatives

semantic_chunking.py
from langchain_experimental.text_splitter import SemanticChunker
from langchain_huggingface import HuggingFaceEmbeddings

emb = HuggingFaceEmbeddings(model_name="sentence-transformers/all-MiniLM-L6-v2")
splitter = SemanticChunker(
    emb, breakpoint_threshold_type="percentile",
    breakpoint_threshold_amount=90, min_chunk_size=200,
)
candidates = splitter.create_documents([text])
# Required next step: enforce the embedding tokenizer's hard maximum.
Packages: langchain-experimental + an embedding integration such as langchain-huggingface. Status: LangChain’s SemanticChunker remains experimental, so its API is less stable; pin and wrap it. Alternatives: LlamaIndex SemanticSplitterNodeParser, semantic-text-splitter, or a custom sentence-window + cosine-distance implementation. Production: conditional—benchmark, cache, and hard-cap output.

4. Docling HybridChunker

docling_hybrid.py
from docling.document_converter import DocumentConverter
from docling.chunking import HybridChunker

EMBED_MODEL = "sentence-transformers/all-MiniLM-L6-v2"
dl_doc = DocumentConverter().convert("manual.pdf").document
chunker = HybridChunker(tokenizer=EMBED_MODEL, max_tokens=480, merge_peers=True)

records = [
    {"text": chunker.contextualize(c), "meta": c.meta.export_json_dict()}
    for c in chunker.chunk(dl_doc=dl_doc)
]
Package: docling (or docling-core[chunking]). Production: high suitability for PDFs/office files; validate OCR/layout quality and align its tokenizer/model identifier with the embedding service.

5. Parent-child retrieval — LangChain

parent_child.py
from langchain.retrievers import ParentDocumentRetriever
from langchain.storage import InMemoryStore
from langchain_text_splitters import RecursiveCharacterTextSplitter

retriever = ParentDocumentRetriever(
    vectorstore=vectorstore, docstore=InMemoryStore(),
    child_splitter=RecursiveCharacterTextSplitter(chunk_size=300, chunk_overlap=30),
    parent_splitter=RecursiveCharacterTextSplitter(chunk_size=1400, chunk_overlap=100),
)
retriever.add_documents(documents)
parents = retriever.invoke("How do I rotate an API key?")
Packages: langchain + langchain-text-splitters and your vector-store integration. Production: pattern is highly suitable; replace in-memory parent storage with a durable store and pin LangChain because import paths can change across releases.

6. Context enrichment — framework-neutral

context_enrichment.py
def embedding_text(chunk: dict) -> str:
    m = chunk["metadata"]
    prefix = f"Document: {m['title']}\nSection: {' > '.join(m['heading_path'])}"
    return f"{prefix}\n\n{chunk['raw_text']}"

record = {
    "chunk_id": stable_chunk_id, "raw_text": raw_text,
    "embedding_text": embedding_text(chunk),
    "metadata": {**chunk["metadata"], "document_version": version},
}
Package: none required. Production: strongly recommended. Keep source-faithful raw text separate from embedding text; enrichment should be concise, deterministic, versioned, and included in token accounting.

7. Late chunking — transformers + torch

late_chunking_core.py
import torch
from torch.nn.functional import normalize
from transformers import AutoModel, AutoTokenizer

name = "jinaai/jina-embeddings-v2-base-en"
tok = AutoTokenizer.from_pretrained(name, trust_remote_code=True)
model = AutoModel.from_pretrained(name, trust_remote_code=True).eval()
batch = tok(document, return_tensors="pt", return_offsets_mapping=True, truncation=True)
offsets = batch.pop("offset_mapping")[0]
with torch.no_grad(): token_vectors = model(**batch).last_hidden_state[0]

# char_spans come from structural/semantic chunk boundaries.
chunk_vectors = []
for start, end in char_spans:
    mask = (offsets[:, 0] < end) & (offsets[:, 1] > start)
    chunk_vectors.append(normalize(token_vectors[mask].mean(0), dim=0))
Packages: transformers, torch; reference implementation: jina-ai/late-chunking. How it differs: encode the long document first, then pool token vectors for chunk spans, so each chunk vector contains surrounding context. Production: advanced/conditional—requires a compatible long-context model, correct offset mapping, high memory, batching, and benchmarked serving/indexing code.
Operational checklist

Important Production Considerations

Most chunking failures in production are lifecycle and observability failures, not splitter-algorithm failures.

📏

Embedding token limits

Use the model’s documented maximum as a hard ceiling—not a target. Reserve tokens for titles, headings, instructions, separators, and special tokens. Track p50/p95/p99 chunk tokens and rejected/truncated counts.

🔤

Tokenizer alignment

The chunker and embedding service should use the same tokenizer and normalization rules. Different subword vocabularies can turn a safe chunk into truncation, especially for code, CJK text, IDs, and tables.

🔁

Chunk overlap

Use overlap to protect facts crossing arbitrary prose boundaries, usually 10–20%. It increases index size, embedding cost, duplicate retrieval, and context waste. Structure-aware and parent-child systems often need less.

▦

Tables and code

Keep caption, headers, units, and rows together; repeat headers when splitting tables. Split code at symbol/class/function boundaries, preserve signatures and imports, and avoid overlapping arbitrary token windows through syntax.

🏷

Metadata

Store source URI, title, heading path, element type, page/coordinates, language, timestamps, access-control labels, parent ID, and raw source offsets. Metadata enables filtering, citations, debugging, and secure retrieval.

🆔

Chunk IDs & versions

Use deterministic IDs such as hash(document stable ID + document version + source span + chunker version). Never overwrite history ambiguously; query only the active document version and support rollback.

🧬

Deduplication

Use exact content hashes before embedding and near-duplicate detection where templates dominate. Preserve provenance lists. At retrieval, collapse siblings/duplicates so repeated boilerplate does not occupy top-K.

♻️

Re-indexing

Build a new versioned index or namespace, backfill idempotently, run shadow queries, compare metrics, then atomically switch an alias. Avoid destructive in-place migration and clean old indexes only after rollback windows expire.

💸

Embedding cost

Estimate total enriched tokens—not document bytes. Overlap, contextual prefixes, duplicate documents, semantic-boundary embeddings, and retries all add cost. Cache by content + model + preprocessing version and batch requests.

📊

Recall@K & Precision@K

Create query-to-relevant-evidence judgments. Recall@K measures whether top K contains the needed chunk; Precision@K measures the fraction of top K that is relevant. Also track MRR/nDCG, answer faithfulness, context tokens, latency, and cost.

Access control: authorization metadata must propagate to every child and parent. Apply permission filters before retrieval results reach reranking or generation; parent expansion must not cross ACL boundaries.
Career preparation

18 Interview Questions

Short model answers focused on practical system-design decisions. Click a question to reveal the answer.

BEGINNER

Foundations

1Why does a RAG system chunk documents?▼
Embedding and generation models have input limits, while whole-document vectors compress too many topics. Chunks provide focused retrieval units so the system can fetch only relevant evidence.
2How would you choose chunk size?▼
Start from the smallest unit that can answer typical queries, then stay below the embedding-token limit with room for enrichment. Benchmark several sizes—often 256, 512, and 768 tokens—using labeled queries and Recall@K/Precision@K rather than intuition.
3What does chunk overlap solve?▼
It duplicates boundary context so a sentence or fact split near an arbitrary edge can still be retrieved intact. It costs extra vectors/tokens and can crowd top-K with duplicates, so use the minimum measured amount.
4Characters or tokens—which should define chunk size?▼
Tokens should enforce the production limit because the embedding model consumes tokens. Character counts are only a fast approximation and vary badly across languages, code, and identifiers.
5What is recursive character chunking?▼
It recursively tries separators from strongest to weakest—paragraphs, lines, spaces, characters—until every chunk fits. It is cheap, deterministic, and a strong baseline, but does not understand layout or topic changes.
6Why store metadata with each chunk?▼
Metadata supports filtering, authorization, citations, parent lookup, provenance, debugging, and re-indexing. At minimum keep document/version IDs, source span, section path, and chunker/model versions.
INTERMEDIATE

Applied design

7When would you use semantic chunking?▼
Use it for narrative or transcript-like text where topics change without reliable headings and a recursive baseline merges unrelated ideas. Avoid paying for it until evaluation shows structure-aware/token-based chunks are insufficient.
8Why can semantic chunking create excessively large chunks?▼
If adjacent sentence windows remain similar, the distance threshold never triggers. The chunk keeps growing beyond model limits, so semantic boundaries require an independent hard token cap and usually a minimum/target size too.
9Why is Docling HybridChunker useful for PDFs?▼
PDFs encode layout rather than logical text. Docling reconstructs hierarchy, reading order, tables, captions, and metadata; HybridChunker then splits oversized structural chunks and merges compatible small peers using the embedding tokenizer.
10How do you handle tables?▼
Keep the caption, units, headers, and row groups together. If rows must be split, repeat headers in every chunk, preserve row boundaries and table coordinates, and consider both a Markdown serialization and a concise table summary.
11How does parent-child chunking work?▼
Small child chunks are embedded for precise matching. Retrieved child IDs point to larger parent sections, which are deduplicated and supplied to the LLM. This separates the optimal retrieval unit from the optimal answer-context unit.
12Why should chunker and embedding tokenizers match?▼
The model limit is expressed in its own tokens. A different tokenizer may undercount and cause silent truncation, changing the meaning of the embedded text and breaking reproducibility.
ADVANCED

Production and evaluation

13How do you evaluate whether one chunking strategy is better?▼
Freeze the parser, embedding model, index, queries, judgments, K, and retrieval settings; change only chunking. Compare Recall@K, Precision@K, MRR/nDCG, answer correctness/faithfulness, context tokens, ingestion cost, storage, and latency by document/query type.
14What is late chunking?▼
It runs a long-context embedding transformer over the document first, then pools token representations for each chunk span. Chunk embeddings therefore retain surrounding context, unlike traditional pre-chunk-then-embed processing.
15How would you combine semantic splitting with HybridChunker?▼
Use Docling to establish hierarchy and protect tables/code. Apply semantic breakpoints only inside oversized narrative sections, then enforce the embedding tokenizer’s maximum and optionally merge tiny peers with the same heading. Structure constrains semantics; tokens have final authority.
16How do you re-index without downtime?▼
Create a new versioned namespace, ingest idempotently, run integrity checks and shadow retrieval evaluation, then atomically move an index alias. Keep the previous index during a rollback window.
17What can go wrong with LLM-based chunking?▼
The model may invent summaries, omit evidence, return invalid or unstable offsets, exceed rate limits, leak sensitive data, or drift after an upgrade. Require structured output, source-span validation, deterministic token caps, caching, model versioning, and fallback logic.
18A strategy improves Recall@10 but answer quality falls. Why?▼
Top-10 may now contain the evidence but also more redundant or irrelevant tokens, causing context dilution or truncation. Inspect Precision@K, parent expansion, duplicate collapse, reranking, context order, and whether the gold evidence survives the final generation budget.
