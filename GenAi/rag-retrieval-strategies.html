Core retrieval concepts

Retrieve Broadly, Select Carefully

Retrieval is not one nearest-neighbor call. Production systems separate fast candidate generation from expensive final context selection.

📐 Similarity search

Cosine compares direction and ignores magnitude; higher is closer. Dot product uses direction and magnitude; higher is closer. Euclidean (L2) measures geometric distance; lower is closer.

cos(q,d) = q·d / (‖q‖ ‖d‖)

For unit-normalized vectors, dot product equals cosine, and squared L2 is monotonically related. Never compare raw scores across models or metrics.

🔢 Top-K retrieval

k is how many nearest results are returned. Choose it from evaluation and downstream capacity—not habit. Small K risks missing evidence; large K raises latency, duplicates, and noise.

Why not Top-5 directly? A reranker cannot recover a relevant chunk that candidate retrieval never returned. Fetch 20–50 cheaply, then select 5–10 accurately.

🎚 Similarity threshold

A minimum score rejects weak matches and supports “no evidence” behavior. It is useful for narrow, calibrated corpora, but fixed values drift with model, metric, query length, language, index, and domain.

accept if calibrated_score ≥ τ

Top-K always returns K, even poor results. Threshold returns a variable count, possibly zero. Production often combines a generous K with a calibrated floor.

🏷 Metadata filtering

Filter by tenant, user, ACL, document/version, date, category, language, page, region, lifecycle state, and source.

  • Pre-filter: database restricts eligible records before/during ANN search—safer and cheaper, but selective filters can reduce ANN recall.
  • Post-filter: filter returned candidates—simple, but may leave too few results and must never be the only security boundary.

🎯 Candidate retrieval vs final context

Candidate retrieval maximizes recall: use fast dense/sparse search to create Top-20/50. Final context maximizes precision per token: apply ACLs, deduplication, reranking, parent expansion, compression, and a token budget to select 5–10.

More candidates can help recall. Sending all candidates to the LLM can reduce answer quality through context dilution and increase prompt cost.

Query transformation

Change the Query Before Search

Transformations can clarify conversational intent, explore alternate vocabulary, or embed a hypothetical answer-shaped passage.

✍️ Query Rewrite

Uses conversation history to make an ambiguous turn standalone.

Input
“What about authentication?”

Rewrite
“How does the FastAPI service validate JWT authentication tokens?”

Best for chat follow-ups. Require the rewrite to preserve entities and avoid answering the question.

🪞 Multi-Query

Generates complementary formulations, retrieves each, then merges IDs, deduplicates, and reranks.

Original: How does JWT authentication work?
1. How are JWT tokens used for authentication?
2. What is the JWT authentication flow?
3. How are JWT tokens validated?

Raises recall when terminology varies, but multiplies retrieval calls and may drift.

🧪 HyDE

An LLM writes a hypothetical answer/document. Embed that passage and use it to retrieve real documents.

Query → hypothetical document → embedding → vector search → real evidence

Answer-like vocabulary can match passages better than a short question. Hallucinated assumptions can pull retrieval toward the wrong neighborhood.

Deep dive

Hybrid Search

Dense search understands paraphrases. Lexical/BM25 search protects exact terminology. Fusion combines their independent rankings.

Dense branch

A bi-encoder maps query and chunks into the same vector space. ANN search finds semantic neighbors even without shared words. It can miss rare identifiers, literal error strings, versions, and newly coined names.

Strong: intent, paraphrase, multilingual semantics.
Weak: exact IDs, code symbols, unseen terminology.

Sparse / BM25 branch

BM25 weights matching terms using term frequency, inverse document frequency, and document-length normalization. Learned sparse encoders also produce term-space vectors, often adding expansion terms.

Strong: CVE IDs, stack traces, product names, function names.
Weak: paraphrases and conceptual similarity.
Dense + BM25 → Reciprocal Rank Fusion
Each branch retrieves independently. RRF combines rank positions without assuming incomparable raw scores share a scale.

RRF

RRF(d) = Σ 1 / (c + rankᵢ(d))

Robust default because it uses rank, not raw scores. c dampens top-rank dominance (often around 60, but tune/evaluate).

Weighted fusion

score = α·dense + (1−α)·sparse

Lets one branch dominate, but requires calibrated or normalized scores. Tune α on labeled queries, ideally by query segment.

Score normalization

min-max · z-score · rank-based

Dense cosine and BM25 do not share a natural scale. Normalize per query/list before weighted addition, and handle outliers/flat lists.

When hybrid beats dense-only: technical documentation, exact error messages, API/class names, SKU/product codes, versions, legal citations, acronyms, and any corpus where exact terminology is evidence—not noise.

Reranking

Initial retrieval is fast and recall-oriented. A reranker spends more computation only on the short candidate list to improve final precision.

Bi-encoder vs cross-encoder

Bi-encoder: encodes query and documents separately, so document vectors are precomputed and ANN search scales. Interaction is compressed into one similarity value.

Cross-encoder: reads [query, document] jointly with full token interaction. It is usually more precise but requires one forward pass per pair.

Reranker choices

  • Sentence Transformers CrossEncoder: local, controllable, good baseline.
  • BGE / FlagEmbedding: strong local multilingual/code rerankers.
  • Cohere Rerank: managed API, simple v2 endpoint.
  • Jina rerankers: managed/local options, multilingual and code-oriented models.
  • LLM reranking: flexible criteria and listwise reasoning, but highest cost, latency, and nondeterminism.
cross_encoder_rerank.py
from sentence_transformers import CrossEncoder

reranker = CrossEncoder("cross-encoder/ms-marco-MiniLM-L6-v2")
pairs = [(query, doc.page_content) for doc in candidates]
scores = reranker.predict(pairs)
ranked = [doc for _, doc in sorted(zip(scores, candidates), key=lambda pair: pair[0], reverse=True)]
final_context = ranked[:8]
Why not rerank the whole database? A cross-encoder is O(number of query-document pairs) at query time and cannot reuse independent document vectors. Reranking one million chunks would be prohibitively slow and expensive; ANN/BM25 narrows the work first.

🗜

Compression vs reranking

Reranking reorders or drops whole candidates. Compression transforms a selected chunk into a shorter query-specific excerpt. A pipeline may rerank first, then compress only the final few documents.

When it helps

Long parents, verbose policies, transcripts, repeated boilerplate, or strict context budgets. Avoid it for short chunks, latency-critical paths, and evidence where extraction could remove qualifiers, exceptions, table structure, or citation spans.

Trade-off: compression reduces prompt tokens but adds an extraction model call and can omit critical caveats. Keep raw text and offsets, require extractive output where possible, and evaluate context recall—not only token savings.

fastapi_retrieval_core.py
from fastapi import FastAPI
from pydantic import BaseModel
from langchain_chroma import Chroma
from langchain_ollama import OllamaEmbeddings
from sentence_transformers import CrossEncoder

app = FastAPI()
emb = OllamaEmbeddings(model="qwen3-embedding:0.6b")
store = Chroma(collection_name="rag_chunks", embedding_function=emb,
               persist_directory="./chroma")
reranker = CrossEncoder("cross-encoder/ms-marco-MiniLM-L6-v2")

class SearchRequest(BaseModel):
    query: str
    tenant_id: str

@app.post("/retrieve")
def retrieve(req: SearchRequest):
    # ACL/tenant filter must be applied by the database, not only afterward.
    candidates = store.similarity_search(
        req.query, k=40, filter={"tenant_id": req.tenant_id, "active": True}
    )
    pairs = [(req.query, d.page_content) for d in candidates]
    scores = reranker.predict(pairs)
    ranked = sorted(zip(scores, candidates), key=lambda x: x[0], reverse=True)
    return [{"text": d.page_content, "metadata": d.metadata}
            for _, d in ranked[:8]]

Always-on stages

  • Authentication, tenant/ACL pre-filtering
  • Stable IDs, active document version filter
  • Candidate retrieval with observability
  • Deduplication and context token budget
  • Citations/provenance and “insufficient evidence” behavior

Optional—gate by evidence

  • BM25/hybrid: exact-term failures justify it
  • Rewrite: ambiguous conversational turns
  • Multi-query/HyDE: difficult low-recall queries
  • Reranker: candidate precision is weak
  • Parent/compression: answer context is incomplete/verbose
Stop adding stages when: offline retrieval and end-to-end answer metrics no longer improve enough to justify p95 latency, infrastructure, token cost, failure modes, and operational ownership. More stages are not inherently more production-ready.
Critical distinction

Candidate Retrieval ≠ Final Context

Candidate generation and context assembly optimize different objectives and should have separate metrics.

Candidate retrieval = maximize recall

Database → Top 20–50 candidates

Use fast ANN, BM25, sparse search, query fan-out, and hybrid fusion. It is acceptable to include some false positives if relevant evidence survives into the pool.

Primary metric: candidate Recall@K / Hit Rate@K.

Final context = maximize value per token

Candidates → filter → dedup → rerank → compress → 5–10

Remove unauthorized, duplicated, weak, or verbose evidence; preserve enough context and citations to answer faithfully within the prompt budget.

Primary metrics: context precision/relevance, context recall, faithfulness, tokens, latency.

Common anti-pattern: retrieving Top-50 and sending all 50 to the LLM. This increases token cost and can bury the strongest evidence among duplicates or contradictions. Broad retrieval is useful only when followed by disciplined selection.

Evidence-driven improvement

Retrieval Evaluation

A “better” retriever must improve labeled retrieval and the final grounded answer without unacceptable latency or cost.

Recall@K

relevant found / relevant total

Did the candidate pool contain all required evidence? Critical for first-stage retrieval.

Precision@K

relevant in K / K

How much of the returned set is relevant? Important for final context.

MRR

mean(1 / first rank)

Rewards putting the first relevant result early. Good for single-answer lookup.

NDCG@K

DCG / ideal DCG

Measures graded relevance and ranking position when results have different usefulness.

Hit Rate@K

queries with ≥1 hit

Simple success rate; does not show whether all evidence was retrieved.

Context relevance

useful context / context

Is selected context focused on the query rather than merely similar?

Context recall

supported claims covered

Does context contain the evidence required for the reference answer?

Answer faithfulness

claims grounded / claims

Does the generated answer stay supported by retrieved evidence?

How to prove an improvement

  1. Build representative queries with document/chunk relevance judgments, multi-hop cases, no-answer cases, and tenant/ACL cases.
  2. Freeze corpus version, chunking, embedding model, index parameters, and generator while changing one retrieval component.
  3. Measure candidate Recall@20/50, final Precision/Recall@5/10, MRR/NDCG, duplicate rate, context tokens, p50/p95 latency, and cost.
  4. Run end-to-end answer correctness, context relevance/recall, citation accuracy, and faithfulness; retrieval gains that do not survive generation are not product gains.
  5. Segment by query type—exact ID, conceptual, conversational, multilingual, multi-hop—then canary online and monitor regressions/drift.
