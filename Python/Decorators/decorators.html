Introduction

What Are Decorators?

A simple pattern that lets you add behavior to functions — without changing them.

What's a Decorator?

A decorator is just a function that wraps another function to add extra behavior — like logging, checking permissions, or measuring time — without changing the original function's code. You slap @decorator_name above your function, and Python handles the rest.

@decorator → func = decorator(func)

Foundations

Key Concepts

You need to know these four things before decorators will click.

📦

First-Class Functions

In Python, functions aren't special — they're just objects like strings or numbers. You can store them in variables, pass them to other functions, or return them. That's it.

greet = say_hello
greet() # same as say_hello()

💡 This is the foundation that makes decorators possible.

🔄

Higher-Order Functions

A function that takes another function as input, or returns a function as output. Decorators do both — they take your function in and give back a new one.

def apply(func, x):
  return func(x)

💡 map(), filter(), sorted() are all higher-order functions.

🔒

Closures

When you define a function inside another function, the inner one can still access variables from the outer one — even after the outer function is done running. That's a closure. Decorators use this trick to hold onto your original function.

def outer(func):
  def inner(): ...
  return inner

💡 The wrapper function is a closure over the original func.

✨

The @ Syntax

Instead of writing my_func = decorator(my_func) manually, you just put @decorator on the line above your function. Python does the rest.

@my_decorator
def my_func(): ...

💡 Equivalent to: my_func = my_decorator(my_func)

🧅 Think of it like peeling an onion

Imagine you write this:

@decorator_A
@decorator_B
@decorator_C
def my_function(): ...

Step 1 — Wrapping (bottom to top): Python reads decorators from the bottom up.

  • @decorator_C wraps my_function first (closest to the function)
  • @decorator_B wraps the result of C
  • @decorator_A wraps the result of B (outermost layer)

Step 2 — Calling (top to bottom, then back up): When you call my_function(), execution goes through the layers like this:

→ A's "before" code runs
  → B's "before" code runs
    → C's "before" code runs
      → original function runs
    ← C's "after" code runs
  ← B's "after" code runs
← A's "after" code runs

Simple analogy: Think of wrapping a gift. You put the gift in a small box (C), then put that box in a medium box (B), then put that in a big box (A). When someone opens it, they open the big box first (A), then the medium box (B), then the small box (C) to reach the gift (your function).

Code Examples

Start simple, then build up. Each example adds one new idea.

Example 1: Basic Decorator

The simplest decorator — just prints something before and after your function runs.

basic_decorator.py 
def greeting_decorator(func):
    def wrapper():
        print("Before the function runs.")
        func()
        print("After the function runs.")
    return wrapper

@greeting_decorator
def say_hello():
    print("Hello, World!")

say_hello()
Before the function runs. Hello, World! After the function runs.

Example 2: Timer Decorator with *args/**kwargs

This one works with any function, no matter how many arguments it takes. Also shows functools.wraps which you should always use.

timer_decorator.py 
import time
import functools

def timer(func):
    """Measure execution time of a function."""
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        start = time.perf_counter()
        result = func(*args, **kwargs)
        elapsed = time.perf_counter() - start
        print(f"⏱ {func.__name__} took {elapsed:.4f}s")
        return result
    return wrapper

@timer
def compute(n):
    return sum(i * i for i in range(n))

result = compute(1_000_000)
print(f"Result: {result}")
⏱ compute took 0.0847s Result: 333332833333500000

Example 3: Decorator Factory — Authentication

Sometimes you want to pass settings to your decorator (like which role is required). That's a decorator factory — a function that builds and returns a decorator.

auth_decorator.py 
import functools

def require_role(role):
    """Decorator factory: restricts access by user role."""
    def decorator(func):
        @functools.wraps(func)
        def wrapper(user, *args, **kwargs):
            if user.get("role") != role:
                raise PermissionError(
                    f"Requires '{role}' role, got '{user['role']}'"
                )
            return func(user, *args, **kwargs)
        return wrapper
    return decorator

@require_role("admin")
def delete_user(user, target_id):
    print(f"✓ User {target_id} deleted by {user['name']}")

admin = {"name": "Alice", "role": "admin"}
delete_user(admin, 42)
✓ User 42 deleted by Alice

Example 4: Advanced — Retry with Exponential Backoff

Network calls fail all the time. This decorator catches errors and retries automatically, waiting a bit longer each time.

retry_decorator.py 
import functools, time, random

def retry(max_attempts=3, backoff=2):
    """Retry with exponential backoff on failure."""
    def decorator(func):
        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            for attempt in range(1, max_attempts + 1):
                try:
                    return func(*args, **kwargs)
                except Exception as e:
                    if attempt == max_attempts:
                        raise
                    wait = backoff ** attempt + random.uniform(0, 1)
                    print(f"⚠ Attempt {attempt} failed: {e}. Retrying in {wait:.1f}s")
                    time.sleep(wait)
        return wrapper
    return decorator

@retry(max_attempts=3, backoff=2)
def fetch_data(url):
    # Simulates unreliable network call
    if random.random() < 0.7:
        raise ConnectionError("Server timeout")
    return {"status": "ok"}
⚠ Attempt 1 failed: Server timeout. Retrying in 2.4s ⚠ Attempt 2 failed: Server timeout. Retrying in 4.7s {'status': 'ok'}

Example 5: Multiple Decorators — Execution Sequence

You can stack multiple decorators on a single function. They wrap from bottom to top, but execute from top to bottom. Here's how the sequence plays out.

multiple_decorators.py 
# First decorator
def decorator1(func):
    def wrapper():
        print("Decorator 1 - Before function is called.")
        func()
        print("Decorator 1 - After function is called.")
    return wrapper

# Second decorator
def decorator2(func):
    def wrapper():
        print("Decorator 2 - Before function is called.")
        func()
        print("Decorator 2 - After function is called.")
    return wrapper

# Applying multiple decorators
@decorator1
@decorator2
def my_function():
    print("Original function.")

# Using the decorated function
my_function()
Decorator 1 - Before function is called. Decorator 2 - Before function is called. Original function. Decorator 2 - After function is called. Decorator 1 - After function is called.

How it works: The decorators are applied bottom-up — decorator2 wraps my_function first, then decorator1 wraps the result. This is equivalent to writing my_function = decorator1(decorator2(my_function)). When called, decorator1's wrapper runs first (outermost layer), then decorator2's wrapper, then the original function. On the way back out, decorator2 finishes first, then decorator1.

In Production

Real-World Use Cases

Decorators are everywhere in Python. Here's where you'll actually use them.

🛡️

Authentication & Authorization

Check if a user is logged in or has the right permissions before letting them access a page or API endpoint.

⏱️

Performance Monitoring

Measure how long functions take to run. Useful for finding slow spots in your code without adding timing logic everywhere.

📝

Logging & Auditing

Automatically print or save what functions were called, with what arguments, and what they returned. Great for debugging.

💾

Caching & Memoization

Save the result of expensive function calls so you don't have to compute the same thing twice. Python has @lru_cache built in for this.

🔄

Retry & Circuit Breaker

If a function fails (like a network request timing out), try it again automatically instead of crashing.

🌐

API Route Registration

In Flask or FastAPI, you use @app.route("/users") to say "this function handles requests to /users". That's a decorator.

✅

Input Validation

Check that function arguments are valid before running the actual logic. Reject bad data early instead of crashing later.

🚦

Rate Limiting

Limit how often someone can call your API — like "max 100 requests per minute". Stops people from abusing your server.

🤖

ML Pipeline Steps

Track which experiments you ran, log accuracy numbers, and version your data transformations — all without cluttering your model code.

Career Prep

Interview Questions

Questions you'll likely get asked. Click to reveal the answers.

1 Can we modify function parameters inside a decorator? ▼

Yes, absolutely. Since the wrapper function receives all arguments via *args and **kwargs before calling the original function, you can freely add, remove, or change any parameter before passing them along.

This is one of the most powerful things about decorators — you can inject data (like a user ID or timestamp), validate inputs, set defaults, or transform values without touching the original function's code.

def my_decorator(func):
  def wrapper(*args, **kwargs):
    # args and kwargs are yours to modify here
    # then pass them to the original function
    return func(*args, **kwargs)
  return wrapper
💡 The key insight: the wrapper sits between the caller and the function — it can intercept and change anything in transit.
2 What's the difference between @decorator and @decorator()? ▼

@decorator passes your function directly to the decorator. @decorator() calls the decorator first (which should return the real decorator). You use parentheses when you need to pass settings, like @retry(max_attempts=3).

💡 Give @app.route("/path") as a real-world decorator factory example.
3 Why is functools.wraps important? ▼

Without it, your decorated function loses its original name and docstring — so help(func) shows "wrapper" instead of the real name, and debugging becomes confusing. Always add @functools.wraps(func) to your wrapper.

💡 Show that you can access the original via func.__wrapped__ when wraps is used.
4 How do stacked decorators execute? ▼

They wrap from bottom to top — the one closest to your function wraps first. But when you call the function, they run from top to bottom. So @A @B @C def f means A's code runs first, then B's, then C's, then your function.

💡 Use the "onion model" analogy — layers wrap from inside out, but peel from outside in.
5 How would you write a decorator that accepts arguments? ▼

You write a function that takes your arguments (like role="admin"), and inside it you define and return the actual decorator. So you end up with three nested functions: the factory, the decorator, and the wrapper.

💡 Draw the three-level nesting on a whiteboard to show clear understanding.
6 Can you use a class as a decorator? How? ▼

Yes. Make a class with __init__ (to receive the function) and __call__ (to act as the wrapper when the function is called). This is handy when your decorator needs to remember things between calls, like counting how many times a function ran.

💡 Mention @dataclass as a built-in class decorator that transforms classes.
7 What is @property and how does it work internally? ▼

@property turns a method into something that looks like a regular attribute. So instead of calling obj.get_name(), you just write obj.name and it runs your method behind the scenes.

💡 Explain the full pattern: @property, @name.setter, @name.deleter.
8 How do decorators affect performance? ▼

Each decorator adds one extra function call, which takes maybe 0.1–0.5 microseconds. You won't notice it in normal code. But if you're decorating something that runs millions of times in a tight loop, it can add up. For most real apps, it's a non-issue.

💡 Quantify the overhead and explain when it matters vs. when it doesn't.
9 How can we modify positional arguments (*args) in a decorator? ▼

args is a tuple, so you can't change it directly. Convert it to a list, make your changes, then pass it to the original function.

Common operations:

  • Add an argument: Insert at any position
  • Change an argument: Replace a value by index
  • Remove an argument: Pop or slice it out
def modify_args(func):
  def wrapper(*args, **kwargs):
    args_list = list(args)

    # Add a new first argument
    args_list.insert(0, "injected_value")

    # Change the second argument
    args_list[1] = args_list[1].upper()

    # Remove the last argument
    args_list.pop()

    return func(*args_list, **kwargs)
  return wrapper
💡 Remember: args is a tuple (immutable). Always convert to a list first with list(args), modify it, then unpack with *args_list.
10 How can we modify keyword arguments (**kwargs) in a decorator? ▼

kwargs is a regular dictionary, so modifying it is straightforward — just add, change, or delete keys like you would with any dict.

Common operations:

  • Add a new kwarg: kwargs['key'] = value
  • Change an existing kwarg: kwargs['key'] = new_value
  • Set a default (only if not provided): kwargs.setdefault('key', default)
  • Remove a kwarg: kwargs.pop('key', None)
def modify_kwargs(func):
  def wrapper(*args, **kwargs):

    # Inject a timestamp if not provided
    kwargs.setdefault('timestamp', time.time())

    # Force a specific value
    kwargs['source'] = 'api'

    # Remove a sensitive field before passing
    kwargs.pop('password', None)

    return func(*args, **kwargs)
  return wrapper

@modify_kwargs
def save_data(data, timestamp=None, source=None):
  print(f"Saving from {source} at {timestamp}")

save_data("hello")
# Output: Saving from api at 1716556800.0
💡 kwargs is already a dict — no conversion needed. Use setdefault() when you want to add a value only if the caller didn't provide one.
