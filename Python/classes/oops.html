Introduction

What Is OOP?

A way to organize code around "things" (objects) instead of just functions and variables.

Object-Oriented Programming in Plain English

OOP is a way of writing code where you bundle data and the functions that work on that data into a single unit called a class. When you create a specific instance of that class, it's called an object. Think of a class as a blueprint (like "Car") and an object as an actual car you can drive.

class = blueprint  |  object = actual thing built from that blueprint

OOP Foundations

The four building blocks you need to understand before anything else clicks.

🏗️

Classes & Objects

A class defines what something is (attributes) and what it can do (methods). An object is a specific instance of that class with actual data filled in.

class Dog:
  def __init__(self, name):
    self.name = name

rex = Dog("Rex") # object

💡 self refers to the specific object being created or used.

🔐

Encapsulation

Hide internal details and expose only what's needed. Use _single underscore for "private by convention" and __double for name mangling (harder to access from outside).

self._internal = "hint: private"
self.__secret = "name-mangled"

💡 Python trusts developers — it's "we're all adults here" philosophy.

🧬

Inheritance

A child class gets all the attributes and methods of a parent class — then adds or overrides what's different. Avoids repeating code.

class Animal: ...
class Dog(Animal): ... # inherits

💡 Use super() to call the parent's methods from the child.

🎭

Polymorphism

Different classes can have the same method name but behave differently. You call .speak() on any animal — a Dog barks, a Cat meows. Same interface, different behavior.

for animal in [dog, cat]:
  animal.speak() # different output

💡 Python uses "duck typing" — if it quacks like a duck, it IS a duck.

variables.py 
class Dog:
    species = "Canis familiaris"  # class variable — shared
    count = 0

    def __init__(self, name, age):
        self.name = name   # instance variable — unique
        self.age = age     # instance variable — unique
        Dog.count += 1    # modify class variable

rex = Dog("Rex", 5)
buddy = Dog("Buddy", 3)

print(rex.name)       # Rex (instance)
print(buddy.name)     # Buddy (instance)
print(rex.species)    # Canis familiaris (shared)
print(Dog.count)      # 2 (shared counter)

Polymorphism in Action

Same method name, different behavior — the caller doesn't need to know which class it's dealing with.

polymorphism.py 
class Animal:
    def speak(self):
        raise NotImplementedError

class Dog(Animal):
    def speak(self):
        return "Woof!"

class Cat(Animal):
    def speak(self):
        return "Meow!"

class Duck(Animal):
    def speak(self):
        return "Quack!"

# Polymorphism — same interface, different behavior
animals = [Dog(), Cat(), Duck()]
for animal in animals:
    print(animal.speak())
Woof! Meow! Quack!
Magic Methods

Dunder Methods

Special methods with double underscores that let your objects work with Python's built-in operations.

What Are Dunder Methods?

"Dunder" means double underscore — like __init__, __str__, __len__. These are hooks that Python calls automatically when you use operators or built-in functions on your objects. Want len(my_obj) to work? Define __len__. Want print(my_obj) to show something useful? Define __str__.

len(obj) → obj.__len__()  |  str(obj) → obj.__str__()  |  obj[i] → obj.__getitem__(i)

📊 Dunder Methods Quick Reference

MethodTriggered ByPurpose
__init__(self, ...)MyClass()Constructor — runs when you create an object. Set up initial state here.
__str__(self)print(obj), str(obj)Human-readable string. What users see.
__repr__(self)repr(obj), REPLDeveloper-readable string. Should ideally recreate the object.
__len__(self)len(obj)Return the "length" of your object.
__call__(self, ...)obj()Makes your object callable like a function.
__iter__(self)for x in objMakes your object iterable in a for loop.
__getitem__(self, key)obj[key]Enables bracket access like lists/dicts.

All Dunder Methods in One Class

A playlist class that implements every dunder method we covered — so you can see them all working together.

dunder_methods.py 
class Playlist:
    def __init__(self, name, songs=None):
        """Constructor — called when you create a Playlist."""
        self.name = name
        self.songs = songs or []

    def __str__(self):
        """Human-readable — for print() and str()."""
        return f"🎵 {self.name} ({len(self.songs)} songs)"

    def __repr__(self):
        """Developer-readable — for debugging."""
        return f"Playlist('{self.name}', {self.songs})"

    def __len__(self):
        """Called by len() — returns song count."""
        return len(self.songs)

    def __getitem__(self, index):
        """Called by playlist[0] — bracket access."""
        return self.songs[index]

    def __iter__(self):
        """Called by for loop — makes it iterable."""
        return iter(self.songs)

    def __call__(self):
        """Called when you do playlist() — like a function."""
        print(f"▶ Now playing: {self.songs[0]}")

# Using all the dunder methods
p = Playlist("Road Trip", ["Bohemian Rhapsody", "Hotel California", "Stairway to Heaven"])

print(p)           # __str__
print(repr(p))     # __repr__
print(len(p))      # __len__
print(p[1])        # __getitem__
p()                 # __call__

for song in p:     # __iter__
    print(f"  - {song}")
🎵 Road Trip (3 songs) Playlist('Road Trip', ['Bohemian Rhapsody', 'Hotel California', 'Stairway to Heaven']) 3 Hotel California ▶ Now playing: Bohemian Rhapsody - Bohemian Rhapsody - Hotel California - Stairway to Heaven
Modern Python

Dataclasses

Write classes with less boilerplate — Python auto-generates __init__, __repr__, and more for you.

Why Dataclasses?

Writing __init__, __repr__, and __eq__ for every class gets tedious. The @dataclass decorator (Python 3.7+) generates all that boilerplate for you. You just declare your fields and Python handles the rest.

@dataclass → auto-generates __init__, __repr__, __eq__ from your field declarations

Dataclass Basics

Before and after — see how much code you save.

❌ Without dataclass (verbose)

without_dataclass.py 
class User:
    def __init__(self, name, email, age):
        self.name = name
        self.email = email
        self.age = age

    def __repr__(self):
        return (f"User(name='{self.name}', "
                f"email='{self.email}', "
                f"age={self.age})")

    def __eq__(self, other):
        return (self.name == other.name
                and self.email == other.email
                and self.age == other.age)

✅ With dataclass (clean)

with_dataclass.py 
from dataclasses import dataclass

@dataclass
class User:
    name: str
    email: str
    age: int

# That's it! __init__, __repr__,
# and __eq__ are auto-generated.

user = User("Alice", "alice@dev.io", 28)
print(user)
# User(name='Alice', email='alice@dev.io', age=28)

Frozen Dataclass — Immutable Objects

Add frozen=True to make your dataclass immutable — like a tuple, but with named fields.

frozen_dataclass.py 
from dataclasses import dataclass

@dataclass(frozen=True)
class Point:
    x: float
    y: float

p = Point(3.0, 4.0)
print(p)          # Point(x=3.0, y=4.0)
print(p.x)        # 3.0

# Can't modify — it's frozen!
# p.x = 10  → FrozenInstanceError!

# Frozen dataclasses are hashable — can be dict keys or set members
points = {p: "origin"}
print(points[Point(3.0, 4.0)])  # "origin"

# Use cases: coordinates, config values, cache keys
@dataclass(frozen=True)
class Color:
    r: int
    g: int
    b: int

RED = Color(255, 0, 0)
BLUE = Color(0, 0, 255)
Point(x=3.0, y=4.0) 3.0 origin

field() and default_factory

Need a mutable default (like a list or dict)? You can't just write tags: list = [] — that's a shared mutable default bug. Use field(default_factory=list) instead.

field_example.py 
from dataclasses import dataclass, field

@dataclass
class BlogPost:
    title: str
    author: str
    views: int = 0                          # simple default
    tags: list = field(default_factory=list)  # mutable default
    metadata: dict = field(default_factory=dict)

    # field() options:
    # - default_factory: callable that creates the default value
    # - repr=False: hide from __repr__ output
    # - compare=False: exclude from __eq__ comparison
    # - init=False: don't include in __init__ params

    _internal: str = field(default="", repr=False)  # hidden from repr

# Each instance gets its OWN list — no shared state bug
post1 = BlogPost("Python OOP", "Alice")
post2 = BlogPost("Decorators", "Bob")

post1.tags.append("python")
post1.tags.append("oop")

print(post1)
print(post2)
print(f"Post1 tags: {post1.tags}")
print(f"Post2 tags: {post2.tags}")  # empty — not shared!
BlogPost(title='Python OOP', author='Alice', views=0, tags=['python', 'oop'], metadata={}) BlogPost(title='Decorators', author='Bob', views=0, tags=[], metadata={}) Post1 tags: ['python', 'oop'] Post2 tags: []

⚠️ Common Bug: Never write tags: list = [] in a dataclass. All instances would share the SAME list. Always use field(default_factory=list) for mutable defaults.

Real-World Examples

Complete examples that show OOP patterns you'll actually use in projects.

Example 1: Bank Account — Encapsulation

A class that protects its balance from direct manipulation — you can only change it through methods.

bank_account.py 
class BankAccount:
    def __init__(self, owner, balance=0):
        self.owner = owner
        self.__balance = balance  # private — can't access directly

    def deposit(self, amount):
        if amount <= 0:
            raise ValueError("Deposit must be positive")
        self.__balance += amount
        return f"Deposited ${amount}. New balance: ${self.__balance}"

    def withdraw(self, amount):
        if amount > self.__balance:
            raise ValueError("Insufficient funds")
        self.__balance -= amount
        return f"Withdrew ${amount}. New balance: ${self.__balance}"

    @property
    def balance(self):
        return self.__balance  # read-only access

    def __str__(self):
        return f"Account({self.owner}: ${self.__balance})"

acc = BankAccount("Alice", 1000)
print(acc.deposit(500))
print(acc.withdraw(200))
print(f"Balance: ${acc.balance}")
print(acc)
Deposited $500. New balance: $1500 Withdrew $200. New balance: $1300 Balance: $1300 Account(Alice: $1300)

Example 2: Shape Hierarchy — Inheritance & Polymorphism

A base class defines the interface, child classes implement the specifics.

shapes.py 
import math

class Shape:
    """Base class — defines what every shape must do."""
    def area(self):
        raise NotImplementedError

    def __str__(self):
        return f"{self.__class__.__name__}: area = {self.area():.2f}"

class Circle(Shape):
    def __init__(self, radius):
        self.radius = radius

    def area(self):
        return math.pi * self.radius ** 2

class Rectangle(Shape):
    def __init__(self, width, height):
        self.width = width
        self.height = height

    def area(self):
        return self.width * self.height

class Square(Rectangle):
    """Square IS a Rectangle with equal sides."""
    def __init__(self, side):
        super().__init__(side, side)  # call parent's __init__

# Polymorphism — same interface, different shapes
shapes = [Circle(5), Rectangle(4, 6), Square(3)]
for shape in shapes:
    print(shape)
Circle: area = 78.54 Rectangle: area = 24.00 Square: area = 9.00

Example 3: Callable Class — __call__ for Stateful Functions

A class that acts like a function but remembers state between calls — perfect for counters, validators, or rate limiters.

callable_class.py 
class Counter:
    """A callable that counts how many times it's been called."""

    def __init__(self):
        self.count = 0
        self.history = []

    def __call__(self, label="default"):
        self.count += 1
        self.history.append(label)
        return f"Call #{self.count} ({label})"

    def __str__(self):
        return f"Counter: {self.count} calls"

# Use it like a function — but it remembers state
counter = Counter()
print(counter("login"))
print(counter("api_call"))
print(counter("api_call"))
print(counter)
print(f"History: {counter.history}")
Call #1 (login) Call #2 (api_call) Call #3 (api_call) Counter: 3 calls History: ['login', 'api_call', 'api_call']

Example 4: Advanced Dataclass — API Response Model

A production-style dataclass with validation, computed fields, and serialization.

api_model.py 
from dataclasses import dataclass, field, asdict
from datetime import datetime
from typing import Optional

@dataclass
class APIResponse:
    status: int
    data: dict
    message: str = "OK"
    timestamp: str = field(default_factory=lambda: datetime.now().isoformat())
    errors: list = field(default_factory=list)
    meta: Optional[dict] = None

    @property
    def is_success(self):
        return 200 <= self.status < 300

    def to_json(self):
        """Convert to dict for JSON serialization."""
        return asdict(self)

# Success response
response = APIResponse(
    status=200,
    data={"user": "Alice", "role": "admin"},
)
print(response)
print(f"Success: {response.is_success}")

# Error response
error = APIResponse(
    status=422,
    data={},
    message="Validation failed",
    errors=["email is required", "age must be positive"]
)
print(f"Errors: {error.errors}")
APIResponse(status=200, data={'user': 'Alice', 'role': 'admin'}, message='OK', timestamp='2026-05-31T10:30:00', errors=[], meta=None) Success: True Errors: ['email is required', 'age must be positive']

Real-World Use Cases

OOP is everywhere in Python. Here's where you'll actually use it.

🌐

Web Framework Models

Django/SQLAlchemy models map database tables to classes. Each row is an object you can query, update, and save.

🎮

Game Entities

API Clients

Configuration Objects

ML Models

📦

Custom Collections

🔒

Context Managers

Classes with __enter__ and __exit__ work with with statements — auto-cleanup for files, connections, locks.

Career Prep

Interview Questions

Questions you'll likely get asked. Click to reveal the answers.

1 What's the difference between a class and an object? ▼

A class is a blueprint — it defines what attributes and methods something will have. An object is a specific instance created from that blueprint with actual data. You can create many objects from one class, each with different values.

Think: class Car is the design spec. my_car = Car("Tesla", "red") is an actual car you can drive.

💡 Say "class defines structure, object holds state" — short and clear.
2 What's the difference between __str__ and __repr__? ▼

__str__ is for humans — what you want users to see when they print the object. __repr__ is for developers — it should ideally be a string that could recreate the object (like User('Alice', 28)).

If only one is defined, Python falls back to __repr__ for both. Always define __repr__ at minimum.

💡 Rule of thumb: __repr__ for debugging, __str__ for display. If in doubt, implement __repr__.
3 How does Python handle private variables? Is anything truly private? ▼

Nothing is truly private in Python. Single underscore (_var) is a convention meaning "don't touch from outside." Double underscore (__var) triggers name mangling — Python renames it to _ClassName__var, making it harder (but not impossible) to access.

Python's philosophy is "we're all consenting adults" — it trusts you to respect conventions rather than enforcing strict access control.

💡 Mention that name mangling exists to prevent accidental name collisions in inheritance, not for security.
4 What is super() and when do you use it? ▼

super() gives you access to the parent class's methods. You use it most often in __init__ to call the parent's constructor before adding your own stuff. Without it, the parent's initialization code wouldn't run.

class Dog(Animal):
  def __init__(self, name, breed):
    super().__init__(name) # call Animal.__init__
    self.breed = breed
💡 Also mention MRO (Method Resolution Order) — super() follows it in multiple inheritance.
5 What's the difference between instance variables and class variables? ▼

Instance variables belong to each object — defined in __init__ with self.x. Each object has its own copy. Class variables are defined in the class body and shared by ALL instances.

Use class variables for constants or counters. Use instance variables for data that's unique to each object.

💡 Gotcha: if you assign to self.class_var, it creates an instance variable that shadows the class variable — it doesn't modify the shared one.
6 What makes __call__ useful? Give a real example. ▼

__call__ lets you use an object like a function — obj() instead of obj.do_something(). It's useful when you need a function that remembers state between calls, like a counter, a rate limiter, or a memoization cache.

Real example: decorators implemented as classes use __call__ — the decorator instance wraps the function, and __call__ runs the wrapper logic each time the function is called.

💡 If you can check callable(obj) and it returns True, the object has __call__ defined.
7 When would you use a dataclass vs a regular class? ▼

Use a dataclass when your class is primarily about storing data — like a config object, API response, or database record. It auto-generates __init__, __repr__, and __eq__ so you don't write boilerplate.

Use a regular class when behavior is more important than data — like a service class with complex methods, or when you need full control over initialization logic.

💡 Rule: if you're writing a class and most of __init__ is just self.x = x, use a dataclass.
8 What is field(default_factory=list) and why is it needed? ▼

In dataclasses, you can't use mutable defaults like tags: list = [] because all instances would share the same list object. field(default_factory=list) creates a new empty list for each instance — solving the shared mutable default bug.

# BAD — shared list bug
tags: list = []

# GOOD — each instance gets its own list
tags: list = field(default_factory=list)
💡 default_factory accepts any callable — list, dict, set, or even a custom function like lambda: [1, 2, 3].
9 Explain polymorphism with a practical example. ▼

Polymorphism means "many forms" — different classes respond to the same method call in their own way. The caller doesn't need to know which specific class it's dealing with.

Practical example: a payment system with CreditCard, PayPal, and Crypto classes. Each has a process_payment(amount) method. Your checkout code just calls payment_method.process_payment(total) — it works regardless of which payment type the user chose.

💡 Python uses "duck typing" — it doesn't check the class, just whether the method exists. If it has .process_payment(), it works.
10 What's the difference between @dataclass(frozen=True) and a regular dataclass? ▼

A frozen dataclass is immutable — you can't change any field after creation. Trying to set an attribute raises FrozenInstanceError. This makes it hashable, so you can use it as a dictionary key or put it in a set.

Use frozen dataclasses for value objects that shouldn't change — coordinates, colors, configuration constants, cache keys.

💡 Frozen dataclasses are Python's answer to "I want a named tuple but with type hints and methods."
11 How do you make a custom object work with for loops? ▼

Implement __iter__ (which returns an iterator) and optionally __next__. The simplest approach is to have __iter__ return iter(self.some_list) — delegating to a built-in iterable.

For custom iteration logic, make your class its own iterator by implementing both __iter__ (returns self) and __next__ (returns next value or raises StopIteration).

💡 Also mention __getitem__ — if you define it, Python can iterate over your object even without __iter__ (it tries index 0, 1, 2... until IndexError).
12 What is MRO (Method Resolution Order) in Python? ▼

MRO is the order Python searches through classes when you call a method. With single inheritance it's simple (child → parent → grandparent). With multiple inheritance, Python uses the C3 linearization algorithm to determine a consistent order.

You can check it with MyClass.__mro__ or MyClass.mro(). This is what super() follows — it doesn't always go to the direct parent, it goes to the next class in the MRO.

💡 The "diamond problem" (two parents share a grandparent) is solved by MRO — each class appears only once in the resolution order.
