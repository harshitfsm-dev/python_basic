Multithreading & Multiprocessing

Threads vs processes vs asyncio — lifecycle, locks, race conditions, IPC, shared memory, and how the free-threaded builds finally let threads use every core.

Start Learning → View Examples
Introduction

Three Ways to Do More at Once

Threads share memory. Processes are isolated and bypass the GIL. Asyncio multiplexes thousands of waits onto one thread.

🧵

Multithreading

Multiple threads within ONE process. They share memory, are lightweight to create, but limited by the GIL for CPU work. Perfect for I/O-bound tasks — network calls, file reads, database queries.

⚙️

Multiprocessing

Multiple processes, each with its own Python interpreter and GIL. True parallelism on multiple cores. Heavier to create, separate memory spaces, but no GIL limitation. Perfect for CPU-bound tasks.

⚡

Asyncio

A single thread running an event loop. Switches only at await, so a task costs kilobytes instead of megabytes. Handles 100,000 concurrent waits — but needs async-native libraries and never uses a second core.

A note on the GIL, up front: for most of Python's history, threads could never run Python bytecode on more than one core at a time. That changed with the free-threaded builds — experimental in 3.13, officially supported in 3.14, still opt-in. Jump to the deep dive →

Thread Basics — Creating and Managing Threads

The threading module gives you real OS threads with a clean Python API.

thread_basics.py 
import threading
import time

def worker(name, delay):
    """A simple worker function."""
    print(f"[{name}] Starting...")
    time.sleep(delay)
    print(f"[{name}] Done after {delay}s")

# Create threads
t1 = threading.Thread(target=worker, args=("Thread-1", 2))
t2 = threading.Thread(target=worker, args=("Thread-2", 1))

# Start threads (moves to Runnable state)
t1.start()
t2.start()

# Wait for both to finish
t1.join()  # blocks until t1 is done
t2.join()

print("All threads finished!")

# Useful thread properties
print(f"Active threads: {threading.active_count()}")
print(f"Current thread: {threading.current_thread().name}")
print(f"t1 alive? {t1.is_alive()}")  # False — it's done

Thread Pools — Reuse Threads Efficiently

Creating threads has overhead. A pool pre-creates a fixed number of threads and reuses them for multiple tasks.

thread_pool.py 
from concurrent.futures import ThreadPoolExecutor
import time

def fetch_url(url):
    """Simulate fetching a URL."""
    time.sleep(0.5)  # simulate network delay
    return f"✓ {url} (200 OK)"

urls = [f"https://api.example.com/page/{i}" for i in range(10)]

# ThreadPoolExecutor — the modern way
start = time.perf_counter()
with ThreadPoolExecutor(max_workers=5) as pool:
    # map() distributes work across the pool
    results = list(pool.map(fetch_url, urls))

elapsed = time.perf_counter() - start
print(f"Fetched {len(results)} URLs in {elapsed:.1f}s")
print(f"(Sequential would take {len(urls) * 0.5:.1f}s)")

# submit() for more control — returns Future objects
with ThreadPoolExecutor(max_workers=3) as pool:
    future = pool.submit(fetch_url, "https://api.example.com/special")
    print(f"Result: {future.result()}")  # blocks until done
Fetched 10 URLs in 1.0s (Sequential would take 5.0s) Result: ✓ https://api.example.com/special (200 OK)

Race Conditions — The Bug That Hides

When two threads modify shared data without coordination, you get unpredictable results. This is a race condition.

Watch counter += 1 Lose an Update
One statement, three bytecodes. The steps light up in the order the interpreter actually ran them.
shared memory  →  counter = 100
1 · LOAD → 100 3 · ADD → 101 5 · STORE 101
2 · LOAD → 100 4 · ADD → 101 6 · STORE 101 💥

Step 2 read before step 5 wrote. Both threads computed 101 from the same stale 100, so step 6 overwrites step 5 with the identical value. Two increments happened; the counter moved by one. That single lost update, repeated thousands of times, is the missing ~112,000 in the output below.

race_condition.py 
import threading

# ❌ BROKEN — Race condition!
counter = 0

def increment_unsafe():
    global counter
    for _ in range(100_000):
        counter += 1  # NOT atomic! (LOAD → ADD → STORE)

threads = [threading.Thread(target=increment_unsafe) for _ in range(5)]
for t in threads: t.start()
for t in threads: t.join()

print(f"Expected: 500,000")
print(f"Got:      {counter}")  # Wrong! Different every run!

# What happened:
# Thread A reads counter = 100
# Thread B reads counter = 100 (same value!)
# Thread A writes counter = 101
# Thread B writes counter = 101 (overwrites A's work!)
Expected: 500,000 Got: 387,421 (varies each run!)

Locks & Synchronization — Fixing Race Conditions

A Lock ensures only one thread can access a critical section at a time. Always use with to avoid forgetting to release.

locks_synchronization.py 
import threading

# ✅ FIXED — Using a Lock
counter = 0
lock = threading.Lock()

def increment_safe():
    global counter
    for _ in range(100_000):
        with lock:  # only one thread at a time here
            counter += 1

threads = [threading.Thread(target=increment_safe) for _ in range(5)]
for t in threads: t.start()
for t in threads: t.join()

print(f"Expected: 500,000")
print(f"Got:      {counter}")  # Always correct!

# Other synchronization primitives:
rlock = threading.RLock()      # reentrant lock (same thread can acquire twice)
sem = threading.Semaphore(3)   # allow up to 3 threads at once
event = threading.Event()      # signal between threads
barrier = threading.Barrier(4) # wait until 4 threads arrive

# Semaphore example — rate limiting
def limited_worker(n):
    with sem:  # max 3 concurrent
        print(f"Worker {n} running")
        import time; time.sleep(1)
Expected: 500,000 Got: 500,000 ✓ Always correct!

Rule: If multiple threads read AND write the same variable, you need a lock. If they only read, no lock needed. Always use with lock: (context manager) — it guarantees the lock is released even if an exception occurs.

Deep Dive

The GIL & Your CPU Cores

Why threads historically never used more than one core — and what changed when Python shipped a build without the GIL.

🔒 What the GIL Actually Is

The Global Interpreter Lock is one mutex per interpreter. A thread must hold it to execute Python bytecode. It exists because CPython objects carry a plain, non-atomic reference count — ob_refcnt. If two threads incremented and decremented that counter at the same time without protection, counts would drift, and objects would be freed while still in use (crash) or never freed at all (leak).

Instead of putting a lock on every object, CPython put one lock around the whole interpreter. That made the interpreter simple and single-threaded code fast — at the cost of never running two threads of Python bytecode simultaneously.

The precise claim: the GIL never stopped you from creating many threads, and it never stopped the OS from putting them on different cores. It stopped more than one of them from running Python bytecode at the same instant. That distinction is the whole story.

Proving It — Same Code, Two Builds

This script reports whether the GIL is active and then scales a CPU-bound workload across threads.

gil_scaling_test.py 
import sys, sysconfig, time, os
from concurrent.futures import ThreadPoolExecutor

def gil_status():
    """Report which build we're running on."""
    free_threaded = bool(sysconfig.get_config_var("Py_GIL_DISABLED"))
    # sys._is_gil_enabled() exists on 3.13+ and reflects the *runtime* state
    enabled = getattr(sys, "_is_gil_enabled", lambda: True)()
    return free_threaded, enabled

def burn(n=6_000_000):
    """Pure-Python CPU work — nothing releases the GIL here."""
    total = 0
    for i in range(n):
        total += i * i
    return total

def timed(workers, tasks=4):
    start = time.perf_counter()
    with ThreadPoolExecutor(max_workers=workers) as pool:
        list(pool.map(lambda _: burn(), range(tasks)))
    return time.perf_counter() - start

if __name__ == "__main__":
    ft, gil_on = gil_status()
    print(f"Python        : {sys.version.split()[0]}")
    print(f"Free-threaded : {ft}")          # True on a 3.13t / 3.14t build
    print(f"GIL enabled   : {gil_on}")      # False = threads run in parallel
    print(f"Cores         : {os.cpu_count()}\n")

    one  = timed(1)
    four = timed(4)
    print(f"1 thread  : {one:.2f}s")
    print(f"4 threads : {four:.2f}s")
    print(f"Speedup   : {one / four:.2f}x")

▼ RUN ON python3.14t (FREE-THREADED)

Free-threaded : True GIL enabled : False Cores : 8 1 thread : 2.15s 4 threads : 0.58s Speedup : 3.71x ← real cores, real parallelism

Diagram 6 — The Three-Phase Rollout (PEP 703)
Where free-threading stands today, and where it's headed
Python ≤ 3.12 — GIL only
No option. CPU-bound parallelism means multiprocessing, a C extension that drops the GIL, or another language.
Python 3.13 — Phase I: experimental
PEP 703 lands. A separate build (--disable-gil, shipped as python3.13t) can run threads in parallel, labelled explicitly experimental. Large single-thread penalty, thin ecosystem support.
Python 3.14 — Phase II: officially supported ← we are here
PEP 779 was accepted in June 2025, dropping the "experimental" label. The free-threaded build is supported but still optional and not the default — you install python3.14t alongside the regular interpreter. Single-thread penalty is down to roughly 10% (about 3% on macOS), memory use around 15–20% higher.
Phase III — free-threaded becomes the default
Not scheduled yet. It needs a future PEP plus broad ecosystem support, since every C extension must be rebuilt and audited for thread safety before the flip can happen.

Getting and Controlling a Free-Threaded Interpreter

The free-threaded interpreter is a separate binary with a t suffix. It installs side by side with the normal one.

setup_free_threaded.sh 
# ── Install (uv is the easiest route) ──────────────────────────
uv python install 3.14+freethreaded
uv venv --python 3.14t

# pyenv
pyenv install 3.14.0t

# Homebrew ships it as a separate formula
brew install python-freethreading

# Building from source
./configure --disable-gil --enable-optimizations
make -j8 && make install

# ── Verify ─────────────────────────────────────────────────────
python3.14t -VV
# Python 3.14.0 free-threading build (main, ...) [Clang ...]

python3.14t -c 'import sys; print(sys._is_gil_enabled())'
# False

# ── Toggle at runtime (free-threaded build only) ───────────────
python3.14t -X gil=1 app.py    # turn the GIL back ON (debugging / bad extension)
python3.14t -X gil=0 app.py    # force it OFF
PYTHON_GIL=0 python3.14t app.py  # same thing via env var

# A C extension that isn't marked free-thread-safe will silently
# re-enable the GIL on import. Catch it with:
PYTHONWARNINGS=default python3.14t -W error::RuntimeWarning app.py

Silent fallback gotcha: importing a C extension built without the Py_mod_gil free-threaded marker makes CPython re-enable the GIL for the whole process. Your parallel speedup vanishes with no error. Always assert sys._is_gil_enabled() is False after your imports, not before.

🚨 No GIL Does Not Mean No Locks

This is the single most common misconception. Removing the GIL removes a performance ceiling, not a correctness guarantee. Race conditions get easier to hit, not harder.

still_need_locks.py 
import threading
from concurrent.futures import ThreadPoolExecutor

# counter += 1 is STILL three bytecodes: LOAD, ADD, STORE.
# On a GIL build a switch between them is unlikely (every ~5ms).
# On a free-threaded build the threads are genuinely simultaneous,
# so the interleaving happens constantly.

counter = 0

def unsafe():
    global counter
    for _ in range(200_000):
        counter += 1          # ❌ loses far more updates without the GIL

# ✅ Still the same fix
lock = threading.Lock()
safe_counter = 0

def safe():
    global safe_counter
    for _ in range(200_000):
        with lock:
            safe_counter += 1

# ✅ Better: don't share mutable state at all.
# Give each thread its own accumulator, combine at the end.
def chunk_sum(rng):
    return sum(rng)        # local only — zero contention, scales linearly

with ThreadPoolExecutor(4) as pool:
    chunks = [range(i, 4_000_000, 4) for i in range(4)]
    total = sum(pool.map(chunk_sum, chunks))

# What free-threading does NOT change:
#   • += / -= on shared variables is not atomic
#   • read-modify-write on a shared dict/list needs a lock
#   • deadlocks are still deadlocks
#   • threading.local() is still how you get per-thread state
# What it DOES guarantee: individual list/dict operations stay
# internally consistent — no interpreter crashes, no corruption.

🧭 Free-Threaded Threads vs Multiprocessing

Free-threading doesn't make multiprocessing obsolete. It gives you a cheaper option for CPU work when your data is large and your tasks need to share it.

Practical rule for today: ship on the default GIL build and keep using multiprocessing for CPU-bound work. Reach for the free-threaded build when process overhead is the actual bottleneck — big shared read-only datasets, low-latency request handling, or fan-out where pickling costs more than the computation. Benchmark both; the ~10% interpreter penalty can eat a modest speedup.

# Python 3.14+ — PEP 734
from concurrent import interpreters
from concurrent.futures import InterpreterPoolExecutor

# ── Low-level API ─────────────────────────────────────────────
interp = interpreters.create()
interp.exec("import math; print(math.factorial(20))")

# Each interpreter has isolated module state and its own GIL,
# so threads driving different interpreters run truly in parallel.

# ── Pool API — same shape as the other executors ───────────────
def crunch(n):
    return sum(i * i for i in range(n))

if __name__ == "__main__":
    with InterpreterPoolExecutor(max_workers=4) as pool:
        results = list(pool.map(crunch, [3_000_000] * 4))
    print(len(results))

# Trade-offs vs the alternatives:
#   • vs processes      → faster startup, one address space, but no
#                         crash isolation and some C extensions break
#   • vs free-threading → parallel on the DEFAULT build, isolation by
#                         default, so far fewer race conditions

#                         interpreters.Queue or channels

Three routes to multiple cores as of Python 3.14: multiprocessing — isolated, works on every version, highest overhead. Subinterpreters — isolated, cheaper, available on the default build. Free-threaded threads — shared memory, zero-copy data sharing, and all the correctness risk that comes with it.

Multiprocessing

Separate processes, process pools, inter-process communication, queues, and shared memory.

Process Basics — True Parallelism

Each process has its own Python interpreter, its own GIL, and its own memory space. They run truly in parallel.

process_basics.py 
import multiprocessing
import os
import time

def cpu_task(name):
    """CPU-intensive work in a separate process."""
    print(f"[{name}] PID: {os.getpid()}, computing...")
    result = sum(i * i for i in range(5_000_000))
    print(f"[{name}] Done!")
    return result

if __name__ == "__main__":
    print(f"Main process PID: {os.getpid()}")
    print(f"CPU cores available: {multiprocessing.cpu_count()}")

    # Create processes
    p1 = multiprocessing.Process(target=cpu_task, args=("P1",))
    p2 = multiprocessing.Process(target=cpu_task, args=("P2",))

    start = time.perf_counter()
    p1.start()  # spawns a new OS process
    p2.start()

    p1.join()   # wait for completion
    p2.join()

    print(f"Both done in {time.perf_counter()-start:.2f}s")
    print(f"(Sequential would take ~2x longer)")

Process Pools — Distribute Work Across Cores

A pool manages a fixed number of worker processes and distributes tasks to them automatically.

process_pool.py 
from concurrent.futures import ProcessPoolExecutor
import time

def process_image(image_id):
    """Simulate CPU-heavy image processing."""
    result = sum(i ** 2 for i in range(2_000_000))
    return f"Image {image_id}: processed ({result})"

if __name__ == "__main__":
    images = list(range(8))

    # Sequential — slow
    start = time.perf_counter()
    for img in images:
        process_image(img)
    seq_time = time.perf_counter() - start

    # Process pool — fast (true parallelism)
    start = time.perf_counter()
    with ProcessPoolExecutor(max_workers=4) as pool:
        results = list(pool.map(process_image, images))
    pool_time = time.perf_counter() - start

    print(f"Sequential:   {seq_time:.2f}s")
    print(f"4 processes:  {pool_time:.2f}s")
    print(f"Speedup:      {seq_time/pool_time:.1f}x")
Sequential: 2.84s 4 processes: 0.78s Speedup: 3.6x

Inter-Process Communication — Queues

Processes don't share memory. Use Queues to safely pass data between them — thread/process-safe by design.

How an Object Actually Crosses a Process Boundary
Nothing is shared — every item is pickled, pushed through a pipe, and rebuilt on the other side
🏭 Producer
process A
📦 pickle.dumps
object → bytes
🔀 OS pipe
Queue buffer
📤 pickle.loads
bytes → object
🛠 Consumer

Each dot is one item making the round trip. Two serialization hops per item is why Queue gets expensive for large payloads — and why shared_memory exists. Compare with threading, where handing an object to another thread is just passing a pointer: zero copies, zero cost.

ipc_queues.py 
import multiprocessing
import time

def producer(queue):
    """Puts items into the queue."""
    for i in range(5):
        item = f"item_{i}"
        queue.put(item)
        print(f"  Produced: {item}")
        time.sleep(0.3)
    queue.put(None)  # sentinel — signals "I'm done"

def consumer(queue):
    """Takes items from the queue."""
    while True:
        item = queue.get()  # blocks until item available
        if item is None:
            break
        print(f"  Consumed: {item}")

if __name__ == "__main__":
    queue = multiprocessing.Queue()  # process-safe queue

    p = multiprocessing.Process(target=producer, args=(queue,))
    c = multiprocessing.Process(target=consumer, args=(queue,))

    p.start()
    c.start()

    p.join()
    c.join()
    print("Producer-Consumer done!")

Shared Memory — When Queues Are Too Slow

For high-performance scenarios, processes can share a block of memory directly — no serialization overhead.

shared_memory.py 
import multiprocessing
from multiprocessing import Value, Array

def increment_shared(shared_counter, lock):
    """Modify shared memory safely."""
    for _ in range(10_000):
        with lock:
            shared_counter.value += 1

def fill_array(shared_arr, start, end):
    """Fill a portion of shared array."""
    for i in range(start, end):
        shared_arr[i] = i * i

if __name__ == "__main__":
    # Value — single shared value
    counter = Value('i', 0)  # 'i' = integer, initial value 0
    lock = multiprocessing.Lock()

    procs = [multiprocessing.Process(target=increment_shared, args=(counter, lock))
             for _ in range(4)]
    for p in procs: p.start()
    for p in procs: p.join()
    print(f"Shared counter: {counter.value}")  # 40,000 ✓

    # Array — shared array
    arr = Array('i', 10)  # 10 integers, initialized to 0
    p1 = multiprocessing.Process(target=fill_array, args=(arr, 0, 5))
    p2 = multiprocessing.Process(target=fill_array, args=(arr, 5, 10))
    p1.start(); p2.start()
    p1.join(); p2.join()
    print(f"Shared array: {list(arr)}")
Shared counter: 40000 Shared array: [0, 1, 4, 9, 16, 25, 36, 49, 64, 81]

IPC Options Summary: Queue — safe, easy, moderate speed. Pipe — fast, two-way, for 2 processes. Value/Array — fastest, shared memory, needs locks. Manager — supports dicts/lists across processes, slowest.

Third Option

Threading vs Asyncio

Both give you concurrency for I/O. They differ in who decides when to switch — and that one difference drives every trade-off.

Diagram 7 — Preemptive vs Cooperative Switching
The single most important distinction between the two models

🧵 Threading — preemptive

The OS scheduler decides. It can suspend your thread between any two bytecodes, at any moment, without asking. You have no control over where a switch happens.

SWITCH CAN HAPPEN ANYWHERE ↓

The cursor is your thread. It gets yanked at red marks — involuntary switch points you can neither see nor predict.

  • Every shared mutation is a potential race
  • You need locks, and you need them in the right order
  • A tight CPU loop can't starve the others
  • Blocking calls just work — nothing to annotate

⚡ Asyncio — cooperative

The event loop runs on one thread and only switches where you wrote await. Between two awaits your code is effectively atomic. You control every switch point.

SWITCH ONLY AT await ↓

The cursor runs straight through and only pauses where you wrote await — explicit, visible, in your source.

  • Far fewer races — you can read the switch points
  • Locks are rarely needed for simple counters
  • One task that forgets to await freezes everything
  • Blocking calls are poison — the whole loop stalls

The Same Job, Written Both Ways

Fetch 500 URLs concurrently. Both finish in about the same time — the difference is cost and control.

threads_vs_asyncio.py 
# ══ VERSION A: threads + a blocking library ═══════════════════
from concurrent.futures import ThreadPoolExecutor
import requests, time

def fetch(url):
    return requests.get(url, timeout=10).status_code

def main_threads(urls):
    # 50 OS threads ≈ 400 MB of virtual stack space
    with ThreadPoolExecutor(max_workers=50) as pool:
        return list(pool.map(fetch, urls))

# ══ VERSION B: asyncio + an async library ═════════════════════
import asyncio, aiohttp

async def fetch_async(session, url):
    async with session.get(url) as resp:   # ← switch point
        return resp.status

async def main_async(urls):
    # 500 coroutines ≈ a couple of MB, one thread
    async with aiohttp.ClientSession() as session:
        async with asyncio.TaskGroup() as tg:   # 3.11+ structured concurrency
            tasks = [tg.create_task(fetch_async(session, u)) for u in urls]
    return [t.result() for t in tasks]

urls = [f"https://httpbin.org/get?i={i}" for i in range(500)]

t0 = time.perf_counter(); main_threads(urls)
print(f"threads : {time.perf_counter()-t0:.1f}s")

t0 = time.perf_counter(); asyncio.run(main_async(urls))
print(f"asyncio : {time.perf_counter()-t0:.1f}s")

# Bump the count to 10,000 and the picture changes completely:
#   threads → thrashing, or OOM / "can't start new thread"
#   asyncio → still one thread, still fine

🧵 Pick threads over asyncio when…

  • Your library is synchronous. requests, psycopg2, boto3, pandas, Pillow, most SDKs. No async driver means no asyncio benefit — threads are the only option that doesn't require a rewrite.
  • You're inside a sync codebase. A Django view, a Flask handler, a CLI, a Tkinter/PyQt app. Going async is contagious: one await forces every caller up the stack to become async too.
  • Concurrency is modest. Fewer than a few hundred simultaneous operations. Thread overhead is irrelevant at that scale and the code stays much simpler.
  • The work is blocking C code that releases the GIL. numpy, hashlib, zlib, lxml, DB drivers. Threads scale on these even on a GIL build. Asyncio cannot help at all.
  • You need preemption. If one task might run a long CPU stretch without awaiting, asyncio stalls every other task. The OS will preempt a thread whether it cooperates or not.
  • You're on a free-threaded build doing CPU work. Asyncio is single-threaded by design and gains nothing from removing the GIL.
  • Simple fire-and-forget background work. A daemon thread doing heartbeats or log flushing beats standing up an event loop.

⚡ Pick asyncio over threads when…

  • Concurrency is in the thousands. Chat servers, WebSockets, long-poll connections, crawlers. Threads run out of memory long before the event loop does.
  • Most connections are idle most of the time. 10,000 open sockets with light traffic is the canonical asyncio workload.
  • You're already in an async framework. FastAPI, Starlette, aiohttp, Sanic. Fighting the framework with threads adds bugs, not throughput.
  • You need real cancellation and timeouts. asyncio.timeout(), task.cancel(), and TaskGroup give structured concurrency. There is no safe way to kill a Python thread from outside.
  • Determinism matters. Explicit switch points make reasoning about shared state tractable, and reproduce bugs far more reliably.
  • Async-native drivers exist for your stack. asyncpg, httpx, aiokafka, redis.asyncio, motor.
  • Memory per connection is the constraint. A coroutine costs kilobytes; a thread costs megabytes.

You Don't Have to Choose — Bridging Both

Real applications mix all three. Asyncio ships explicit bridges for exactly this.

bridging.py 
import asyncio, time, requests
from concurrent.futures import ProcessPoolExecutor

# ── 1. Blocking call inside async code → asyncio.to_thread (3.9+) ──
async def good():
    # requests is sync. to_thread hands it to a worker thread so the
    # event loop keeps serving everything else.
    resp = await asyncio.to_thread(requests.get, "https://python.org")
    return resp.status_code

async def bad():
    # ❌ Blocks the loop. Every other task stops for 2 seconds.
    time.sleep(2)                      # use: await asyncio.sleep(2)
    return requests.get("https://python.org").status_code

# ── 2. CPU-bound work inside async code → a process pool ───────────
def crunch(n):
    return sum(i * i for i in range(n))

async def cpu_from_async():
    loop = asyncio.get_running_loop()
    with ProcessPoolExecutor() as pool:
        # run_in_executor keeps the loop responsive while cores burn
        results = await asyncio.gather(*[
            loop.run_in_executor(pool, crunch, 5_000_000) for _ in range(4)
        ])
    return results

# ── 3. Async work from a *sync* thread → run_coroutine_threadsafe ──
def from_a_worker_thread(loop, coro):
    """Call this from any thread that is NOT running the loop."""
    fut = asyncio.run_coroutine_threadsafe(coro, loop)
    return fut.result(timeout=10)      # blocks this thread only

# ── 4. Cap how many threads asyncio will use ───────────────────────
from concurrent.futures import ThreadPoolExecutor

async def with_bounded_pool():
    loop = asyncio.get_running_loop()
    with ThreadPoolExecutor(max_workers=10) as pool:
        loop.set_default_executor(pool)   # to_thread now uses this pool
        await asyncio.gather(*[
            asyncio.to_thread(requests.get, "https://python.org")
            for _ in range(100)
        ])

# ── 5. Find the blocking calls you missed ──────────────────────────
asyncio.run(good(), debug=True)
# Warns: "Executing <Task...> took 2.001 seconds" for any coroutine
# that hogs the loop longer than loop.slow_callback_duration.

The #1 asyncio bug: calling blocking code inside a coroutine. time.sleep(), requests.get(), open().read(), a sync DB driver, or a heavy loop over a big list all halt every task on the loop, not just the current one. Symptom: your async server is somehow slower than the threaded version it replaced. Run with debug=True to find the offenders.

🧠 One-Line Mental Model

Multiprocessing buys you more cores. Asyncio buys you more concurrent waits. Threading buys you concurrent waits without rewriting your libraries — and on a free-threaded build, more cores too.

Or shorter: asyncio scales connections, multiprocessing scales computation, threading is the pragmatic middle that works with the code you already have.

import urllib.request
import time

def fetch(url):

Example 2: Producer-Consumer with Thread-Safe Queue

The classic pattern — one thread produces data, another consumes it, connected by a thread-safe queue.

producer_consumer.py 
import threading
import queue
import time
import random

def producer(q, num_items):
    """Produces items and puts them in the queue."""
    for i in range(num_items):
        item = f"task_{i}"
        time.sleep(random.uniform(0.1, 0.3))
        q.put(item)
        print(f"  [Producer] Added: {item} (queue size: {q.qsize()})")
    q.put(None)  # poison pill — signals "stop"

def consumer(q):
    """Consumes items from the queue."""
    while True:
        item = q.get()  # blocks until item available
        if item is None:
            break
        time.sleep(0.2)  # simulate processing
        print(f"  [Consumer] Processed: {item}")
        q.task_done()

# queue.Queue is thread-safe — no locks needed!
q = queue.Queue(maxsize=5)  # bounded queue (blocks if full)

prod = threading.Thread(target=producer, args=(q, 6))
cons = threading.Thread(target=consumer, args=(q,))

prod.start()
cons.start()
prod.join()
cons.join()
print("Done! All items processed.")

Example 3: Parallel Image Processing (Multiprocessing)

CPU-heavy work distributed across cores — the multiprocessing sweet spot.

parallel_processing.py 
from concurrent.futures import ProcessPoolExecutor, ThreadPoolExecutor
import time

def heavy_computation(n):
    """Simulate CPU-heavy image processing."""
    return sum(i ** 2 for i in range(n))

if __name__ == "__main__":
    tasks = [2_000_000] * 8  # 8 heavy tasks

    # Sequential
    start = time.perf_counter()
    [heavy_computation(t) for t in tasks]
    seq = time.perf_counter() - start

    # Threads (limited by GIL — no speedup for CPU work)
    start = time.perf_counter()
    with ThreadPoolExecutor(4) as pool:
        list(pool.map(heavy_computation, tasks))
    thread = time.perf_counter() - start

    # Processes (bypasses GIL — real speedup!)
    start = time.perf_counter()
    with ProcessPoolExecutor(4) as pool:
        list(pool.map(heavy_computation, tasks))
    proc = time.perf_counter() - start

    print(f"Sequential:     {seq:.2f}s")
    print(f"4 Threads:      {thread:.2f}s (GIL blocks parallelism)")
    print(f"4 Processes:    {proc:.2f}s (true parallelism!)")
    print(f"\nProcess speedup: {seq/proc:.1f}x")

Example 4: Deadlock — What It Is and How to Avoid It

A deadlock happens when two threads each hold a lock the other needs — both wait forever.

deadlock_prevention.py 
import threading

lock_a = threading.Lock()
lock_b = threading.Lock()

# ❌ DEADLOCK — Thread 1 holds A, wants B. Thread 2 holds B, wants A.
# def thread1():
#     with lock_a:
#         with lock_b:  # waits forever — thread2 has lock_b
#             ...
# def thread2():
#     with lock_b:
#         with lock_a:  # waits forever — thread1 has lock_a
#             ...

# ✅ FIX 1: Always acquire locks in the same order
def safe_thread1():
    with lock_a:
        with lock_b:
            print("Thread 1: got both locks")

def safe_thread2():
    with lock_a:  # same order as thread1!
        with lock_b:
            print("Thread 2: got both locks")

# ✅ FIX 2: Use timeout
def timeout_thread():
    if lock_a.acquire(timeout=1):
        try:
            if lock_b.acquire(timeout=1):
                try:
                    print("Got both!")
                finally:
                    lock_b.release()
            else:
                print("Couldn't get lock_b — backing off")
        finally:
            lock_a.release()

t1 = threading.Thread(target=safe_thread1)
t2 = threading.Thread(target=safe_thread2)
t1.start(); t2.start()
t1.join(); t2.join()
print("No deadlock!")
Thread 1: got both locks Thread 2: got both locks No deadlock!

Deadlock prevention rules: (1) Always acquire locks in a consistent global order. (2) Use timeouts. (3) Avoid holding multiple locks when possible. (4) Use threading.RLock() if the same thread needs to acquire a lock it already holds.

Career Prep

Interview Questions

Common concurrency questions. Click to reveal answers.

1 What's the difference between a thread and a process? ▼

A thread is a lightweight unit of execution within a process — threads share the same memory space. A process is a separate program with its own memory, its own Python interpreter, and its own GIL. Threads are cheap to create but limited by the GIL. Processes are heavier but achieve true parallelism.

💡 Analogy: threads are like multiple tabs in one browser (shared memory). Processes are like separate browser windows (isolated memory).
2 What is a race condition and how do you prevent it? ▼

A race condition occurs when two threads access shared data concurrently and at least one modifies it — the result depends on the timing of thread execution. Prevent it with: threading.Lock() for mutual exclusion, queue.Queue for thread-safe data passing, or atomic operations.

💡 The key insight: counter += 1 is NOT atomic — it's three operations (load, add, store). The GIL can switch threads between any of them.
3 What is a deadlock? How do you avoid it? ▼

A deadlock happens when two or more threads are each waiting for a lock held by the other — nobody can proceed. Four conditions must all be true: mutual exclusion, hold-and-wait, no preemption, and circular wait.

Prevention: Always acquire locks in the same order, use timeouts (lock.acquire(timeout=1)), minimize lock scope, or use lock-free data structures like queue.Queue.

💡 In interviews, mention the "dining philosophers" problem as the classic deadlock example.
4 When would you use threading vs multiprocessing vs asyncio? ▼

Threading: I/O-bound tasks with moderate concurrency (10-100 tasks) — web scraping, file I/O, DB queries.

Multiprocessing: CPU-bound tasks — image processing, data crunching, ML training.

Asyncio: High-concurrency I/O (1000+ connections) — web servers, chat apps, WebSocket handlers.

💡 Simple rule: waiting on network → threading/asyncio. Crunching numbers → multiprocessing. Thousands of connections → asyncio.
5 What is a thread pool and why use one? ▼

A thread pool pre-creates a fixed number of worker threads and reuses them for multiple tasks. Benefits: avoids the overhead of creating/destroying threads for each task, limits resource usage (you won't accidentally spawn 10,000 threads), and provides a clean API via ThreadPoolExecutor.

Use max_workers to control pool size. For I/O-bound work, a good default is min(32, os.cpu_count() + 4) (Python's default).

💡 concurrent.futures gives you the same API for both thread pools and process pools — just swap ThreadPoolExecutor ↔ ProcessPoolExecutor.
6 How do processes communicate if they don't share memory? ▼

Inter-Process Communication (IPC) options in Python:

  • multiprocessing.Queue — thread/process-safe, FIFO, uses pickle
  • multiprocessing.Pipe — fast two-way channel between 2 processes
  • multiprocessing.Value/Array — shared memory (fastest, needs locks)
  • multiprocessing.Manager — shared dicts/lists (slowest, most flexible)
  • multiprocessing.shared_memory — raw shared memory blocks (Python 3.8+)
💡 Start with Queue (simplest). Use shared memory only when Queue is too slow (large data, high frequency).
7 What's the difference between Lock, RLock, Semaphore, and Event? ▼

Lock: Basic mutual exclusion — one thread at a time. If the same thread tries to acquire it twice, it deadlocks.

RLock: Reentrant lock — the same thread CAN acquire it multiple times (must release the same number of times). Useful for recursive functions.

Semaphore: Allows up to N threads simultaneously. Like a parking lot with N spots — when full, others wait.

Event: A flag that threads can wait on. One thread sets it, others wake up. Good for signaling "start" or "stop".

💡 Use Lock for protecting shared data. Semaphore for rate limiting. Event for coordination signals. RLock when you have nested locking.
8 What is a daemon thread? ▼

A daemon thread runs in the background and is automatically killed when all non-daemon threads finish. The main thread is non-daemon. Set thread.daemon = True before starting it.

Use cases: background logging, heartbeat checks, cache cleanup. The key behavior: your program won't wait for daemon threads to finish before exiting — they just get killed.

t = threading.Thread(target=background_task)
t.daemon = True  # dies when main thread exits
t.start()
💡 If you need cleanup before exit, don't use daemon threads — use regular threads with proper shutdown signals.
9 Why is if __name__ == "__main__" required for multiprocessing on Windows/macOS? ▼

On Windows and macOS (with "spawn" start method), new processes are created by importing the main module. Without the guard, the child process would re-execute the module-level code — including creating MORE child processes — causing an infinite recursion of process spawning.

Linux uses "fork" by default (copies the parent process), so it often works without the guard — but it's best practice to always include it for portability.

💡 Always wrap multiprocessing code in if __name__ == "__main__": — it's not optional on Windows/macOS.
10 How do you handle exceptions in threads/processes? ▼

Exceptions in threads/processes don't propagate to the main thread automatically. With raw threading.Thread, the exception is silently swallowed. With concurrent.futures, exceptions are captured and re-raised when you call future.result().

with ThreadPoolExecutor() as pool:
  future = pool.submit(risky_function)
  try:
    result = future.result()  # raises if function raised
  except Exception as e:
    print(f"Task failed: {e}")
💡 Always use concurrent.futures over raw threads — it handles exception propagation, timeouts, and cancellation for you.
11 Why couldn't Python threads use multiple cores, and what changed? ▼

The GIL is one mutex per interpreter, and a thread must hold it to run Python bytecode. Threads were always real OS threads that the kernel could place on any core, but only the GIL holder could execute — so total bytecode throughput was capped at one core.

The GIL existed because CPython's ob_refcnt is a plain, non-atomic integer. Concurrent increments and decrements would corrupt it, causing premature frees or leaks.

What changed: PEP 703 replaced the one coarse lock with fine-grained mechanisms — biased reference counting, immortal objects (PEP 683), deferred refcounting, per-object critical sections, QSBR for lock-free container reads, and mimalloc with per-thread free lists. Python 3.13 shipped that as an experimental build; PEP 779 was accepted in June 2025 and made it officially supported in 3.14. It is still an opt-in build (python3.14t), not the default.

💡 Precise phrasing scores points: the GIL never prevented threads from being scheduled on multiple cores — it prevented more than one from executing Python bytecode simultaneously. That's why numpy and other C extensions that release the GIL always scaled with threads.
12 Does the free-threaded build mean you no longer need locks? ▼

No — the opposite. Removing the GIL removes a performance ceiling, not a correctness guarantee. counter += 1 is still LOAD, ADD, STORE. On a GIL build a switch between those bytecodes was possible but rare; on a free-threaded build the threads are genuinely simultaneous, so lost updates become the common case rather than the rare one.

What free-threading does guarantee is internal consistency: individual list and dict operations won't corrupt the interpreter. Your application-level invariants are still entirely your problem.

💡 Best answer: "you still need locks, and the better move is to avoid shared mutable state entirely — per-thread accumulators combined at the end scale linearly and can't race."
13 Threading vs asyncio — where can a context switch happen? ▼

Threading is preemptive: the OS scheduler can suspend a thread between any two bytecodes, at any time, without your consent. You cannot see or predict switch points, which is exactly why race conditions are so easy to introduce.

Asyncio is cooperative: one thread, one event loop, and control transfers only at await. Between two awaits your code is effectively atomic, so you rarely need a lock. The cost is that any task which doesn't await — a blocking call or a tight CPU loop — starves every other task on the loop.

💡 The trade-off in one line: threads give you safety from starvation but expose you to races; asyncio gives you safety from races but exposes you to starvation.
14 What happens if you call time.sleep() or requests.get() inside a coroutine? ▼

The entire event loop stops. Not just that coroutine — every task, every pending connection, every timer. The loop runs on one thread, and a blocking call refuses to give that thread back. A 2-second time.sleep() in one request handler adds 2 seconds of latency to all 5,000 open connections.

Fixes: use the async equivalent (await asyncio.sleep(), httpx/aiohttp instead of requests), or push the blocking call to a thread with await asyncio.to_thread(fn, *args). For CPU-bound work use loop.run_in_executor(process_pool, fn, *args).

💡 Run with asyncio.run(main(), debug=True) — it logs a warning for any callback that exceeds loop.slow_callback_duration, which is how you find the blocking calls you missed.
15 If asyncio runs on one thread, how is it faster than sequential code? ▼

It isn't faster at computing anything — it's faster at waiting. Sequential code waits for one network response at a time. The event loop registers all pending sockets with the kernel (epoll on Linux, kqueue on BSD/macOS, IOCP on Windows), asks in a single syscall which ones are ready, and runs those tasks. Ten thousand waits overlap on one thread.

This is also why asyncio gives you nothing for CPU-bound work: there's no waiting to overlap, and only one thread to run on. A free-threaded build doesn't help either — asyncio is single-threaded by design.

💡 Concurrency is doing many things in overlapping time windows. Parallelism is doing many things at the same instant. Asyncio gives you concurrency only; multiprocessing (and free-threaded threading) gives you parallelism.
16 What are subinterpreters and where do they fit alongside threads and processes? ▼

Subinterpreters are multiple independent Python interpreters inside a single OS process. PEP 684 gave each one its own GIL in Python 3.12, and PEP 734 exposed them in the standard library as concurrent.interpreters in Python 3.14, along with InterpreterPoolExecutor in concurrent.futures.

They sit between threads and processes: because each interpreter has its own GIL, they achieve real multi-core parallelism, but they start faster than a process and stay in one address space. Isolation is a feature — module state isn't shared — so you pass data through an interpreter queue rather than mutating shared objects.

💡 Three routes to multiple cores now: processes (isolated, works everywhere), subinterpreters (isolated, cheaper, 3.14+), free-threaded threads (shared memory, fastest data sharing, most correctness risk).
