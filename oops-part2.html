Contracts

Abstract Classes

Force child classes to implement specific methods — or they can't be created at all.

What's an Abstract Class?

An abstract class is a class you can't instantiate directly. It exists only to be inherited from. It defines a contract — "any class that inherits from me MUST implement these methods." If a child class forgets to implement one, Python raises TypeError at instantiation time, not at runtime.

from abc import ABC, abstractmethod → define the contract

The ABC Module — Defining Contracts

Use ABC as a base class and @abstractmethod to mark methods that MUST be implemented.

abstract_classes.py 
from abc import ABC, abstractmethod

class PaymentProcessor(ABC):
    """Abstract base class — defines the payment interface."""

    @abstractmethod
    def process_payment(self, amount):
        """Must be implemented by all payment processors."""
        pass

    @abstractmethod
    def refund(self, transaction_id):
        """Must be implemented — handle refunds."""
        pass

    def validate_amount(self, amount):
        """Concrete method — shared by all subclasses."""
        if amount <= 0:
            raise ValueError("Amount must be positive")
        return True

# ✅ This works — implements all abstract methods
class StripePayment(PaymentProcessor):
    def process_payment(self, amount):
        self.validate_amount(amount)
        return f"Stripe: charged ${amount}"

    def refund(self, transaction_id):
        return f"Stripe: refunded {transaction_id}"

# ❌ This crashes — missing refund()
class BrokenPayment(PaymentProcessor):
    def process_payment(self, amount):
        return "paid"
    # forgot refund() — TypeError on instantiation!

stripe = StripePayment()
print(stripe.process_payment(99.99))
print(stripe.refund("txn_123"))

# broken = BrokenPayment()  # TypeError: Can't instantiate!
Stripe: charged $99.99 Stripe: refunded txn_123

Interface-Like Behavior

Python doesn't have a formal interface keyword like Java. But an abstract class with ONLY abstract methods (no concrete implementations) acts exactly like one.

interface_pattern.py 
from abc import ABC, abstractmethod

# This acts like an interface — pure contract, no implementation
class Serializable(ABC):
    @abstractmethod
    def to_json(self) -> str:
        pass

    @abstractmethod
    def from_json(cls, data: str):
        pass

class Cacheable(ABC):
    @abstractmethod
    def cache_key(self) -> str:
        pass

# A class can "implement" multiple interfaces
class User(Serializable, Cacheable):
    def __init__(self, name, email):
        self.name = name
        self.email = email

    def to_json(self):
        import json
        return json.dumps({"name": self.name, "email": self.email})

    def from_json(cls, data):
        import json
        d = json.loads(data)
        return cls(d["name"], d["email"])

    def cache_key(self):
        return f"user:{self.email}"

user = User("Alice", "alice@dev.io")
print(user.to_json())
print(user.cache_key())
{"name": "Alice", "email": "alice@dev.io"} user:alice@dev.io

Key difference: An abstract class CAN have concrete methods (shared logic). An interface-like class has ONLY abstract methods (pure contract). Use abstract classes when you want to share code. Use interface-like patterns when you just want to enforce a contract.

Composition

Mixins

Small, focused classes that add reusable behavior — like plugins you snap onto any class.

What's a Mixin?

A mixin is a small class that provides a specific piece of functionality — like logging, serialization, or timestamp tracking. You don't use it alone. You "mix it in" to other classes via multiple inheritance. Think of it like adding a USB adapter to a laptop — it adds capability without changing the core design.

class MyClass(MixinA, MixinB, BaseClass): ... → adds behavior from mixins

Reusable Behavior with Mixins

Each mixin adds one specific capability. Mix and match as needed.

mixins.py 
import json
from datetime import datetime

# Mixin 1: Adds JSON serialization
class JsonMixin:
    def to_json(self):
        return json.dumps(self.__dict__, default=str)

    def __repr__(self):
        return self.to_json()

# Mixin 2: Adds timestamp tracking
class TimestampMixin:
    def __init_subclass__(cls, **kwargs):
        super().__init_subclass__(**kwargs)
        original_init = cls.__init__

        def new_init(self, *args, **kw):
            original_init(self, *args, **kw)
            self.created_at = datetime.now()
            self.updated_at = datetime.now()

        cls.__init__ = new_init

    def touch(self):
        self.updated_at = datetime.now()

# Mixin 3: Adds validation
class ValidatorMixin:
    def validate(self):
        for field, value in self.__dict__.items():
            if value is None:
                raise ValueError(f"{field} cannot be None")
        return True

# Combine mixins with a base class
class User(JsonMixin, ValidatorMixin):
    def __init__(self, name, email):
        self.name = name
        self.email = email

user = User("Alice", "alice@dev.io")
print(user.to_json())       # from JsonMixin
print(user.validate())      # from ValidatorMixin
{"name": "Alice", "email": "alice@dev.io"} True
Composition vs Inheritance — When to Use What
Two ways to reuse code. Pick the right one based on the relationship.

🧬 Inheritance — "IS A"

Use when the child truly IS a type of the parent.

  • Dog IS an Animal ✅
  • Square IS a Rectangle ✅
  • Admin IS a User ✅
class Dog(Animal): ...

🧩 Composition — "HAS A"

Use when the class USES another class as a component.

  • Car HAS an Engine ✅
  • User HAS an Address ✅
  • Game HAS a Player ✅
class Car:
  self.engine = Engine()

Rule of thumb: Prefer composition over inheritance. Inheritance creates tight coupling — if the parent changes, all children break. Composition is more flexible — you can swap components at runtime.

Deep Magic

Metaclasses

Classes that create classes. The deepest level of Python's object system.

What's a Metaclass?

In Python, everything is an object — including classes themselves. A metaclass is the "class of a class." Just like a class defines how objects behave, a metaclass defines how classes behave. The default metaclass is type. When you write class Foo:, Python actually calls type('Foo', bases, attrs) behind the scenes.

object → instance of a class  |  class → instance of a metaclass  |  type → the default metaclass

type() — The Class Factory

type() does two things: check an object's type, or dynamically create a new class.

type_function.py 
# Usage 1: Check type of an object
print(type(42))          # <class 'int'>
print(type("hello"))     # <class 'str'>

# Usage 2: Create a class dynamically!
# type(name, bases, attrs) → creates a new class

# This:
Dog = type("Dog", (), {
    "species": "Canis familiaris",
    "bark": lambda self: "Woof!"
})

# Is EXACTLY the same as writing:
# class Dog:
#     species = "Canis familiaris"
#     def bark(self): return "Woof!"

rex = Dog()
print(rex.species)     # Canis familiaris
print(rex.bark())      # Woof!
print(type(rex))        # <class '__main__.Dog'>
print(type(Dog))        # <class 'type'> ← Dog's class is type!
<class 'int'> <class 'str'> Canis familiaris Woof! <class '__main__.Dog'> <class 'type'>

Custom Metaclass — Practical Example

A metaclass that automatically registers all subclasses — useful for plugin systems, ORMs, and serialization frameworks.

metaclass_example.py 
class RegistryMeta(type):
    """Metaclass that auto-registers all classes created with it."""
    registry = {}

    def __new__(mcs, name, bases, namespace):
        cls = super().__new__(mcs, name, bases, namespace)
        if bases:  # don't register the base class itself
            RegistryMeta.registry[name] = cls
        return cls

# Base class uses our metaclass
class Plugin(metaclass=RegistryMeta):
    pass

# Every subclass is auto-registered — no manual step needed!
class AuthPlugin(Plugin):
    def run(self):
        return "Checking auth..."

class CachePlugin(Plugin):
    def run(self):
        return "Checking cache..."

class LogPlugin(Plugin):
    def run(self):
        return "Logging request..."

# See all registered plugins — no manual list needed!
print("Registered plugins:", list(RegistryMeta.registry.keys()))

# Instantiate and run all plugins dynamically
for name, plugin_cls in RegistryMeta.registry.items():
    plugin = plugin_cls()
    print(f"  {name}: {plugin.run()}")
Registered plugins: ['AuthPlugin', 'CachePlugin', 'LogPlugin'] AuthPlugin: Checking auth... CachePlugin: Checking cache... LogPlugin: Logging request...

⚠️ When to use metaclasses: Almost never in application code. They're for framework authors — Django uses them for models, SQLAlchemy for table mapping, pytest for test discovery. If you're not building a framework, __init_subclass__ or class decorators are simpler alternatives.

Under the Hood

Python Internals

How Python manages memory, cleans up objects, and executes your code.

🧠 Memory Management Overview

Python handles memory automatically — you don't malloc/free like in C. But understanding HOW it works helps you write efficient code and avoid memory leaks.

Python uses a private heap managed by its memory manager. It has three layers of defense against memory waste:

  1. Reference Counting — tracks how many variables point to each object
  2. Garbage Collector — catches circular references that ref counting misses
  3. Memory Pools — pre-allocates small blocks to avoid OS overhead

Reference Counting — The Primary Mechanism

Every object has a counter tracking how many references point to it. When it hits zero, the memory is freed immediately.

reference_counting.py 
import sys

# Create an object — ref count starts at 1
a = [1, 2, 3]
print(sys.getrefcount(a))  # 2 (a + getrefcount's temp ref)

# Add another reference — count goes up
b = a
print(sys.getrefcount(a))  # 3 (a + b + temp)

# Put it in a list — count goes up again
c = [a]
print(sys.getrefcount(a))  # 4 (a + b + c[0] + temp)

# Delete a reference — count goes down
del b
print(sys.getrefcount(a))  # 3

# When ref count hits 0 → memory freed immediately
# No waiting for garbage collector!

# The problem: circular references
class Node:
    def __init__(self):
        self.ref = None

node_a = Node()
node_b = Node()
node_a.ref = node_b  # a → b
node_b.ref = node_a  # b → a (circular!)

# Even after del, ref count never hits 0
# That's where the garbage collector steps in
2 3 4 3

Garbage Collection — Catching Circular References

The GC runs periodically to find and clean up objects that reference each other but are no longer reachable from your code.

garbage_collection.py 
import gc

# Check GC status
print(f"GC enabled: {gc.isenabled()}")
print(f"Thresholds: {gc.get_threshold()}")
# (700, 10, 10) → gen0 after 700 allocs, gen1 after 10 gen0 runs, etc.

# Generational collection: 3 generations
# Gen 0: new objects (collected most often)
# Gen 1: survived one collection
# Gen 2: long-lived objects (collected rarely)

# Force a collection
collected = gc.collect()
print(f"Objects collected: {collected}")

# Create a circular reference
class Circular:
    def __init__(self, name):
        self.name = name
        self.ref = None
    def __del__(self):
        print(f"  Destroying {self.name}")

a = Circular("A")
b = Circular("B")
a.ref = b
b.ref = a

# Remove our references
del a, b

# Objects still exist (circular ref keeps count > 0)
# Force GC to find and clean them
print("Running GC...")
gc.collect()
GC enabled: True Thresholds: (700, 10, 10) Objects collected: 0 Running GC... Destroying A Destroying B

Example 1: Plugin System with Abstract Base Class

A notification system where each channel (email, SMS, push) must implement the same interface.

notification_system.py 
from abc import ABC, abstractmethod

class Notifier(ABC):
    """All notification channels must implement these methods."""

    @abstractmethod
    def send(self, recipient, message):
        pass

    @abstractmethod
    def validate_recipient(self, recipient) -> bool:
        pass

    def notify(self, recipient, message):
        """Template method — shared logic."""
        if not self.validate_recipient(recipient):
            return f"❌ Invalid recipient: {recipient}"
        return self.send(recipient, message)

class EmailNotifier(Notifier):
    def validate_recipient(self, recipient):
        return "@" in recipient

    def send(self, recipient, message):
        return f"📧 Email to {recipient}: {message}"

class SMSNotifier(Notifier):
    def validate_recipient(self, recipient):
        return recipient.startswith("+") and len(recipient) >= 10

    def send(self, recipient, message):
        return f"📱 SMS to {recipient}: {message}"

# Polymorphism — same interface, different channels
notifiers = [EmailNotifier(), SMSNotifier()]
for n in notifiers:
    print(n.notify("alice@dev.io", "Hello!"))
    print(n.notify("+1234567890", "Hello!"))
📧 Email to alice@dev.io: Hello! ❌ Invalid recipient: +1234567890 ❌ Invalid recipient: alice@dev.io 📱 SMS to +1234567890: Hello!

Example 2: Mixins — Building a Feature-Rich Model

Compose behavior from multiple mixins — each adds one capability without inheritance headaches.

mixin_composition.py 
import json
from datetime import datetime

class SerializeMixin:
    """Adds to_dict() and to_json() to any class."""
    def to_dict(self):
        return {k: v for k, v in self.__dict__.items()
                if not k.startswith("_")}

    def to_json(self):
        return json.dumps(self.to_dict(), default=str)

class AuditMixin:
    """Tracks creation and modification times."""
    def __init__(self, *args, **kwargs):
        super().__init__(*args, **kwargs)
        self.created_at = datetime.now()
        self.updated_at = datetime.now()

    def mark_updated(self):
        self.updated_at = datetime.now()

class CompareMixin:
    """Adds equality comparison based on all attributes."""
    def __eq__(self, other):
        if type(self) != type(other):
            return False
        return self.__dict__ == other.__dict__

# Compose all mixins into one class
class Product(SerializeMixin, AuditMixin, CompareMixin):
    def __init__(self, name, price):
        self.name = name
        self.price = price
        super().__init__()  # triggers AuditMixin

p = Product("Widget", 29.99)
print(p.to_dict())
print(f"Created: {p.created_at}")
{'name': 'Widget', 'price': 29.99, 'created_at': datetime(2026, 5, 31, ...), 'updated_at': datetime(2026, 5, 31, ...)} Created: 2026-05-31 10:30:00.123456

Example 3: Memory Profiling — Slots vs Regular Classes

Use __slots__ to reduce memory usage when you have many instances of the same class.

memory_slots.py 
import sys

# Regular class — uses __dict__ for attributes (flexible but heavy)
class PointRegular:
    def __init__(self, x, y):
        self.x = x
        self.y = y

# Slotted class — fixed attributes (less flexible but lighter)
class PointSlotted:
    __slots__ = ['x', 'y']

    def __init__(self, x, y):
        self.x = x
        self.y = y

# Compare memory usage
regular = PointRegular(1, 2)
slotted = PointSlotted(1, 2)

print(f"Regular: {sys.getsizeof(regular)} + {sys.getsizeof(regular.__dict__)} (dict) bytes")
print(f"Slotted: {sys.getsizeof(slotted)} bytes (no __dict__)")

# With 1 million points, slots saves ~40% memory
print(f"\nRegular has __dict__: {hasattr(regular, '__dict__')}")
print(f"Slotted has __dict__: {hasattr(slotted, '__dict__')}")

# Slotted can't add new attributes dynamically:
# slotted.z = 3  → AttributeError!
regular.z = 3  # This works fine on regular class
Regular: 48 + 104 (dict) bytes Slotted: 48 bytes (no __dict__) Regular has __dict__: True Slotted has __dict__: False

Example 4: Composition Over Inheritance

Instead of inheriting behavior, inject it as components — more flexible and easier to test.

composition.py 
from abc import ABC, abstractmethod

# Define interfaces for components
class Engine(ABC):
    @abstractmethod
    def start(self): pass

class ElectricEngine(Engine):
    def start(self):
        return "⚡ Electric motor humming"

class GasEngine(Engine):
    def start(self):
        return "🔥 Gas engine roaring"

class GPS:
    def navigate(self, destination):
        return f"📍 Navigating to {destination}"

# Car USES components (composition) instead of BEING them (inheritance)
class Car:
    def __init__(self, model, engine: Engine, gps: GPS = None):
        self.model = model
        self.engine = engine      # HAS an engine
        self.gps = gps            # HAS a GPS (optional)

    def drive(self, destination=None):
        result = [f"🚗 {self.model}: {self.engine.start()}"]
        if self.gps and destination:
            result.append(self.gps.navigate(destination))
        return "\n".join(result)

# Swap components easily — no inheritance changes needed
tesla = Car("Tesla", ElectricEngine(), GPS())
mustang = Car("Mustang", GasEngine())

print(tesla.drive("San Francisco"))
print()
print(mustang.drive())
🚗 Tesla: ⚡ Electric motor humming 📍 Navigating to San Francisco 🚗 Mustang: 🔥 Gas engine roaring

Career Prep

Interview Questions

Advanced questions you'll get in senior-level interviews. Click to reveal answers.

1 What's the difference between an abstract class and an interface in Python? ▼

Python doesn't have a formal interface keyword. An abstract class (using ABC) can have both abstract methods (contract) AND concrete methods (shared implementation). An "interface" in Python is just an abstract class with ONLY abstract methods — pure contract, no implementation.

Use abstract classes when you want to share code between subclasses. Use interface-like patterns when you just want to enforce a contract without dictating implementation.

💡 Also mention Python's Protocol (typing module) for structural subtyping — "if it has these methods, it satisfies the protocol" without inheritance.
2 What's a mixin and how is it different from regular inheritance? ▼

A mixin is a small class that provides a specific piece of functionality — it's not meant to stand alone. The difference from regular inheritance: a mixin doesn't represent an "is-a" relationship. A User isn't a JsonMixin — it just HAS JSON serialization capability.

Conventions: name them with "Mixin" suffix, keep them focused on one thing, don't store state, and list them before the base class in the inheritance order.

💡 Give Django REST Framework as a real example — class UserView(ListModelMixin, CreateModelMixin, GenericAPIView).
3 When would you choose composition over inheritance? ▼

Use inheritance when there's a genuine "is-a" relationship (Dog IS an Animal). Use composition when there's a "has-a" relationship (Car HAS an Engine) or when you want to swap behavior at runtime.

Prefer composition when: you need flexibility, the relationship might change, you want to avoid deep inheritance hierarchies, or you need to combine behaviors from multiple sources without multiple inheritance complexity.

💡 The "favor composition over inheritance" principle exists because inheritance creates tight coupling — changing the parent breaks all children.
4 What is a metaclass and when would you use one? ▼

A metaclass is a "class of a class" — it controls how classes are created. The default metaclass is type. You'd use a custom metaclass to: auto-register classes, validate class definitions at creation time, inject methods/attributes, or implement ORMs.

In practice, you almost never need them in application code. They're for framework authors. Simpler alternatives: __init_subclass__, class decorators, or descriptors.

💡 Famous quote: "If you're wondering whether you need a metaclass, you don't." — Tim Peters
5 How does Python's garbage collector work? ▼

Python uses two mechanisms: reference counting (primary) and generational garbage collection (secondary). Reference counting frees objects immediately when no references remain. The GC handles circular references that ref counting can't detect.

The GC uses three generations — new objects start in gen 0 (collected frequently). If they survive a collection, they move to gen 1, then gen 2 (collected rarely). This is based on the observation that most objects die young.

💡 Mention that you can control the GC with gc.disable(), gc.collect(), and gc.get_threshold() — useful for performance-critical sections.
6 What's the difference between stack and heap memory in Python? ▼

The stack stores function call frames and local variable references (pointers). It's fast, auto-managed (LIFO), and each thread gets its own. The heap stores all actual Python objects — strings, lists, class instances, everything.

When you write x = [1, 2, 3], the variable x (a reference/pointer) lives on the stack, but the actual list object lives on the heap. Python's memory manager handles heap allocation.

💡 Key insight: Python variables are always references (pointers on the stack) to objects (on the heap). Assignment copies the reference, not the object.
7 Explain Python's execution model — what happens when you run a .py file? ▼

Four stages: (1) Lexing/Parsing — source code is tokenized and parsed into an Abstract Syntax Tree (AST). (2) Compilation — AST is compiled to bytecode (stored in __pycache__/*.pyc). (3) Execution — the Python Virtual Machine (PVM) interprets bytecode instructions one by one. (4) The PVM is a stack-based interpreter.

Python is NOT purely interpreted — it compiles to bytecode first. The .pyc cache means subsequent runs skip compilation if the source hasn't changed.

💡 Use dis.dis(func) to see the bytecode for any function. Use compile() and ast.parse() to inspect intermediate stages.
8 What is __slots__ and when should you use it? ▼

__slots__ tells Python to use a fixed-size array instead of a __dict__ for instance attributes. This saves ~30-50% memory per instance and slightly speeds up attribute access. The trade-off: you can't add new attributes dynamically.

Use it when: you have millions of instances of the same class (like data points, pixels, or database rows) and memory is a concern. Don't use it for regular classes where flexibility matters more than memory.

💡 Gotcha: __slots__ doesn't inherit — each class in the hierarchy needs its own __slots__ declaration.
9 What is the GIL and how does it affect Python programs? ▼

The Global Interpreter Lock (GIL) is a mutex in CPython that allows only one thread to execute Python bytecode at a time. This means multi-threaded Python code can't achieve true parallelism for CPU-bound tasks — even on multi-core machines.

Workarounds: Use multiprocessing for CPU-bound work (separate processes, each with its own GIL). Use threading for I/O-bound work (the GIL is released during I/O operations like network calls). Use asyncio for concurrent I/O.

💡 The GIL exists because CPython's memory management (reference counting) isn't thread-safe. It simplifies the interpreter but limits parallelism.
10 How does type() relate to metaclasses? ▼

type IS the default metaclass. When you write class Foo:, Python internally calls type('Foo', (object,), {...}) to create the class object. A custom metaclass is just a subclass of type that overrides __new__ or __init__ to customize class creation.

# The hierarchy:
type(42)        # → int (42 is an instance of int)
type(int)       # → type (int is an instance of type)
type(type)      # → type (type is an instance of itself!)
💡 The fact that type(type) is type is the bootstrap — it's turtles all the way down, but it stops at type.
11 What's __init_subclass__ and how is it a simpler alternative to metaclasses? ▼

__init_subclass__ (Python 3.6+) is a hook that runs whenever a class is subclassed. It gives you most of the power of metaclasses — auto-registration, validation, attribute injection — without the complexity.

class Plugin:
  registry = []

  def __init_subclass__(cls, **kwargs):
    super().__init_subclass__(**kwargs)
    Plugin.registry.append(cls)

class MyPlugin(Plugin): ... # auto-registered!
💡 Rule: if __init_subclass__ can do what you need, use it instead of a metaclass. It's simpler, more readable, and easier to debug.
12 How can you detect and prevent memory leaks in Python? ▼

Common causes: circular references (especially with __del__), global caches that grow forever, unclosed file handles, and event listeners that hold references.

Detection tools:

  • tracemalloc — built-in memory tracing
  • objgraph — visualize object reference graphs
  • gc.get_objects() — list all tracked objects
  • weakref — create references that don't prevent GC

Prevention: Use weakref for caches, context managers for resources, avoid circular references, and set cache size limits.

💡 In long-running services, periodically log len(gc.get_objects()) — if it grows without bound, you have a leak.
